# 边界情况处理记录

记录分布式执行过程中出现过的边界情况、当前处理方式和后续方向。
原则：框架只负责与测试程序无关的通用逻辑；与具体测试程序相关的策略（重试、失败处理）尽量下沉到插件。

## 1. stp 文件执行失败

现象：某个 stp 文件执行失败（OpenCppCoverage 退出码非 0、cobertura 解析失败、点集入库失败），但任务本身正常上报。

当前处理（保持不变）：

- 客户端：逐文件执行并记录 `FileCoverage.ok=false`，任务结果照常上报；
- 服务端覆盖率插件：只做任务级派发，不处理文件级失败；失败文件被忽略，不影响任务派发；
- 影响：失败文件不贡献覆盖点，不会被选进最小 stp 集合，累计覆盖率缺少对应行；日志保留 `file ... failed` 可事后排查。

后续方向（记录，暂不实施）：

- 文件级失败处理（重试/跳过）由覆盖率客户端插件负责；
- 服务端插件只管理任务级重试（任务丢失、客户端离线、租约超时等由框架回收并重新派发）。

## 2. 波次结算失败（cov 合并失败）

现象：波次 0 全部任务完成后，一次性合并 1000 个 cov 文件命令过长，合并失败，导致后续任务请求不下发。

处理：

- 治标：cov 合并改为两两合并，避免命令行超长（已在内网验证）；
- 语义（已确认）：结算失败 → 结算链暂停，`settle_failed_wave` 记录失败波次；任务派发不受影响，照常下发；待结算队列清空；重启不自动重试，失败态人工介入；
- 结算与任务下发解耦：结算在结果处理线程上异步执行（单结算循环 + 结算队列），不持有主锁，不阻塞心跳、任务请求、结果处理。


## 2.5 多波次并发派发

- 所有波次的任务从 run 开始就全部进入派发池，波次只作为结算批次存在；
- 派发不设波次窗口：客户端有能力且服务端有任务就派发；
- 旧的“wave N+1 在 wave N 结果全部回收后才派发”的门控不再存在；多波次在飞时，后面的波次可以比前面的波次先完成结果回收；
- 结算仍然严格按波次顺序串行（结算队列），wave N+1 的 merge 一定在 wave N 之后；
- 迟到的、属于已结算波次的结果会被丢弃，不会二次触发结算。
## 3. 重复 / 迟到结果

- 框架层：`in_flight` 管理防止同一任务重复派发给两个客户端；
- 插件层：结算队列按波次去重，同一个波次只结算一次；迟到/重复结果不会二次触发结算。

## 4. stop / quit 与结算并发

- `stop`：先向客户端发送 STOP，回收在飞任务，然后 `saveCheckpoint` 等待在飞结算收尾，再 `cancel` 插件；
- `quit`：等价于对每个活跃 run 执行 stop，等待活跃 run 归零后销毁框架（EventManager 清空排队事件、join 工作线程，正在执行的事件跑完）；
- 约定：`saveCheckpoint` 拿到的永远是稳定状态（结算已完成或已暂停）。
