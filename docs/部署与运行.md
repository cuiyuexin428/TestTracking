# 部署与运行

面向部署运维人员。前提：**Windows x64**；命令以 PowerShell 为主，需要提权的步骤已标注。

- 客户端侧的首装与批量升级见 [基础客户端与批量部署](基础客户端与批量部署.md)。
- 方案、制品与滚动发布见 [部署方案与资源管理](部署方案与资源管理.md)。
- 边界与已知问题见 [已知限制](已知限制.md)。

## 1. 端口与目录约定

| 用途 | 默认端口 | 配置位置 |
| --- | --- | --- |
| 调度器 ROUTER | 5555 | `runtime/scheduler.json` 的 `server.router_endpoint`（如 `tcp://*:5555`） |
| 调度器管理 HTTP（仅本机） | 5556 | `runtime/scheduler.json` 的 `server.management_endpoint` |
| 结果服务网页 / 部署 API | 56330 | `runtime/result_service.json` 的 `host` / `port` |
| PostgreSQL | 5432 | `runtime/scheduler.json` 与 `runtime/result_service.json` 的 `db_conn` |

目录约定（一键部署生成，`tools/setup_offline_server.ps1`）：

```text
<项目根>/
  runtime/
    scheduler.json             调度器配置（重新编译 Release 不会覆盖）
    result_service.json        结果服务配置
    client.template.json       未打包客户端时的配置模板
    source_launch.json         记录 bin 目录与被托管数据库
    dataset/                   已准备的数据集（含 manifest.txt、version.txt）
    logs/                      调度器与结果服务日志
    pgdata/                    一键部署托管的 PostgreSQL 数据目录
    python/                    便携 Python（结果服务与分析）
    python-analysis-wheelhouse/ 离线分析依赖 wheelhouse
    start_server.bat           启动调度器 + 结果服务
    start_result_service.bat   只启动结果服务
    stop_result_service.bat    停止结果服务
  dist/client_package/         默认客户端包输出目录
```

**`runtime/` 整体是生成物目录**：其中的配置、日志、pgdata、启动脚本都不属于源码交付内容，源码归档会排除 `runtime` 根下的文件（仅保留 `dataset`、`python`、`python-analysis-wheelhouse` 等源输入）。

## 2. 前置条件

1. Visual Studio 2022 + CMake ≥ 3.16（若要在一键部署里编译）。
2. `tools/offline_deploy.json` 里的实际部署参数（见下一节）。
3. 若使用随包 PostgreSQL：`third_party/pgsql`，或 `third_party_src/downloads/postgresql-*.zip`（脚本会解压到 `runtime/pgsql`）。
4. 结果服务需要 Python 与 `psycopg`：一键部署默认从本地 wheelhouse 安装到 `runtime/python`，不联网。
5. 需要跨机访问时以管理员身份开放端口（脚本会尝试 `netsh advfirewall`，失败时只告警）。

## 3. 一键离线部署

### 3.1 配置 `tools/offline_deploy.json`

关键键（`tools/setup_offline_server.ps1` 全部读取此文件，命令行参数可覆盖）：

| 键 | 作用 |
| --- | --- |
| `build_config` | 构建配置，部署只允许 `Release` |
| `server_ip` | 留空则自动探测本机 IPv4；写入客户端 endpoint 与服务端监听提示 |
| `server_port` / `management_port` / `result_port` / `db_port` | 四个端口，必须互不相同 |
| `db_name` / `db_user` / `db_password` / `db_auth_method` / `client_cidr` | 数据库与 `pg_hba` 远程规则 |
| `dataset_dir` / `dataset_version` | 数据集源目录与版本；会被暂存到 `runtime/dataset` 并重建 manifest |
| `plugin` | `coverage` 或 `stpcompare` |
| `step_test_exe` / `opencppcoverage_dir` / `engine_src_dir` / `engine_dlls` / `program_version` | coverage 的程序与采集工具 |
| `baseline_converter_exe` / `candidate_converter_exe` / `baseline_program_version` / `candidate_program_version` | stpcompare 的两个转换程序 |
| `package_out_dir` / `worker_id` / `task_threads` / `task_size` / `store_cov` | 客户端包输出与执行参数 |
| `dsh_command` | 自定义 DSH CLI 路径（留空用 `dsh`） |
| `register_db_service` | 是否注册 PostgreSQL Windows 服务 |

**不要**把 `dataset_dir` 指向 `runtime/dataset` 或其子目录——脚本会先清理暂存目录再复制，指向自身会破坏数据源（`tools/README.md` 明确提示）。

### 3.2 执行

```powershell
# 以管理员身份运行，便于注册数据库服务与开放防火墙
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1
```

脚本按序执行（`tools/setup_offline_server.ps1` 头部说明与实际顺序一致）：

1. 校验工具链并编译（Release）；
2. 安装/初始化/启动随包 PostgreSQL 并创建数据库；
3. 暂存 STP 数据集并重建 `manifest.txt`；
4. 写 `runtime/scheduler.json`（数据库、管理端口、日志、插件 expected 字段）；
5. 生成完整客户端包（`skills`、程序、数据、OpenCppCoverage，按 `plugin` 分支）；
6. 从本地 wheelhouse 离线安装 Python 分析依赖；
7. 开放防火墙并生成 `runtime/*.bat` 启动入口。

常用开关：`-SkipBuild`、`-SkipDatabase`、`-SkipDataset`、`-SkipPackage`、`-SkipFirewall`、`-SkipPythonAnalysis`、`-NoService`、`-StartScheduler`。**复用已准备的数据时用 `-SkipDataset`**，避免重新覆盖数据源。

### 3.3 部署后自检

```powershell
# 配置文件是否生成
Test-Path .\runtime\scheduler.json, .\runtime\result_service.json

# 端口监听（调度器 5555、管理 5556、网页 56330；数据库 5432）
Get-NetTCPConnection -State Listen -LocalPort 5555,5556,56330,5432 -ErrorAction SilentlyContinue |
    Select-Object LocalAddress,LocalPort

# 结果服务健康检查
Invoke-RestMethod http://127.0.0.1:56330/healthz
Invoke-RestMethod http://127.0.0.1:56330/readyz

# 调度器本机管理快照（只看本机）
Invoke-RestMethod http://127.0.0.1:5556/status | Select-Object online,instance_id,snapshot_age_ms
```

`snapshot_age_ms` 是调度器状态快照的年龄：数值持续增长说明 worker 线程没能刷新状态，应先看 `runtime/logs/scheduler.log`。

## 4. 启动与停止

| 操作 | 命令 | 说明 |
| --- | --- | --- |
| 启动调度器 + 网页 | `runtime\start_server.bat` | 联合入口；系统重启后会按需启动被托管的数据库实例 |
| 只启动网页 | `runtime\start_result_service.bat` | 调度器退出后网页仍可查询数据库与生成报告 |
| 停止网页 | `runtime\stop_result_service.bat` | 依据 PID 文件停止，并校验该 PID 确实属于本结果服务 |

健康检查与故障定位：网页 `/healthz`、`/readyz`；启动脚本会探测端口与进程（`tools/source_services.ps1`）。若结果服务报"结果服务已在运行"，先确认 PID 文件指向的进程仍是本实例。

## 5. 数据库

### 5.1 一键部署托管的实例

脚本用 `initdb -A trust` 初始化 `runtime/pgdata`，改写 `postgresql.conf` 的 `port` 与 `listen_addresses`，并只重写通用远程规则：

- 保留 initdb 生成的 loopback（`127.0.0.1/32`、`::1/128`）条目；
- 追加一条带标记注释的 `host    all    all    <client_cidr>    <db_auth_method>` 规则，旧的同类规则会被清理；
- `-AuthMethod` 非 `trust` 时，本机探测（走 `127.0.0.1`）仍然命中 loopback 规则，不受影响。

### 5.2 独立数据库

```powershell
# 只创建数据库（默认 psql 路径可在参数里覆盖）
powershell -ExecutionPolicy Bypass -File .\tools\init_database.ps1 -DbHost 127.0.0.1 -DbPort 5432 `
    -DbName testtracking -DbUser postgres
```

框架启动时会自行创建/补齐自己的表结构（`runs`、`tasks`、`plugin_task_completions` 等）；插件在各自 `init()` 中创建业务表。因此**建库即可，无需手工建表**。

### 5.3 允许远程客户端直连数据库

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\setup_postgres_remote.ps1
```

之后再用 `tools\build_package.ps1` 打包，脚本会自动探测本机 IPv4 并把 endpoint 与 `db_conn` 写入客户端配置。客户端不使用共享目录时，SMB 相关配置可以不做。

### 5.4 数据库口令与安全

- `db_password` 会被写进 `runtime/scheduler.json`、`runtime/result_service.json`、`runtime/client.template.json` 以及客户端包的 `config/client.json`。
- 这些文件都位于**生成物目录**，源码归档不会带走 `runtime` 根下的文件，客户端包也不应上传到公共位置。
- `docs/` 或工单里不要粘贴真实连接串。

## 6. 运行检查

### 6.1 调度器

```powershell
# 前端界面（推荐）
Invoke-RestMethod http://127.0.0.1:56330/api/scheduler | ConvertTo-Json -Depth 6

# 直接问调度器管理端口
$body = @{ action = 'run'; plugin_type = 'coverage'; dataset_version = 'd1' } | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:5556/commands -Method Post -ContentType 'application/json' -Body $body
```

- 运行命令支持 `worker_ids`（精确的调度器客户端身份数组）；空或缺省表示允许该插件的全部兼容客户端。
- 停止 run 必须带 run ID，避免陈旧页面停掉更新的 run。
- 调度器 stdin 也支持 `run <plugin_type> <dataset_version> [params]` 与 `stop <plugin_type>`（仅调试用）。

### 6.2 结果服务

```powershell
Invoke-RestMethod http://127.0.0.1:56330/api/plugins
Invoke-RestMethod http://127.0.0.1:56330/api/agents
Invoke-RestMethod http://127.0.0.1:56330/api/deployments
```

只读查询侧的其它常用入口：

| 入口 | 用途 |
| --- | --- |
| `GET /api/runs`、`GET /api/runs/<run_id>` | 运行列表与单次运行详情（`plugin`、`limit`（默认 50）、`offset`、`search` 过滤） |
| `GET /api/plugins/<plugin>/view` | 插件的声明式结果视图；`PUT` 同一路径可更新，必须带上读取时的 `revision` |
| `GET /api/plugins/<plugin>/report-script` | 报告脚本源码与 revision；`PUT` 同一路径保存完整 `source` + revision + `operator_id` |
| `GET /api/plugins/<plugin>/reports?run_id=` | 该插件（指定运行）最近一次成功报告 |
| `POST /api/plugins/<plugin>/reports` | 生成报告；产物页面为 `/reports/<report_id>/index.html` |
| `GET /api/analysis/catalog` | 助手用的运行、结果完整性与表结构目录（`plugin`、`limit`、`offset`、`search`） |
| `GET /api/analysis/runs/<run_id>?plugin=` | 单次运行的分析就绪信息（必须给出已知插件） |
| `GET /api/logs` | 列出 `logs_dir` 下的日志文件（有界截断、不接受任意路径） |

视图与报告脚本的 `PUT` 都采用"读 revision → 带 revision 保存"的并发约定：他人先保存时返回 409 与 `current_revision`，保留草稿、重新读取后再合并保存，**不要**用新 revision 直接重放旧草稿。

- 日志页只读 `logs_dir` 下的文件；调度器要写日志必须配置 `server.log_file`。
- 调度器离线时，`/api/agents`、`/api/scheduler` 会给出明确错误，数据库结果、报告与助手仍可用。

### 6.3 覆盖率后处理

```powershell
# 只算精简集合
powershell -ExecutionPolicy Bypass -File .\tools\settle_coverage.ps1 -Run <run_id> -Db "<连接串>"

# 额外合并二进制报告（需要 OpenCppCoverage）
powershell -ExecutionPolicy Bypass -File .\tools\settle_coverage.ps1 -Run <run_id> -Db "<连接串>" `
    -MergeCov -OpenCppCoverage <OpenCppCoverage.exe 路径> [-WorkDir <父目录>]
```

- 该工具会先取会话级 advisory lock，同一 run 不会被并发后处理。
- 合并阶段有 10 分钟超时，且按轮次分别计时（每轮 10 分钟）。
- 失败时旧结果保持不变，可重试。

### 6.4 运行数据清理

```powershell
# 默认保留最近 10 个终态 run 的历史，其余清理
powershell -ExecutionPolicy Bypass -File .\tools\prune_old_runs.ps1

# 先看会删什么；-Keep 控制保留数量
powershell -ExecutionPolicy Bypass -File .\tools\prune_old_runs.ps1 -Keep 20 -DryRun
```

清理范围是 `finished`/`cancelled`/`interrupted`/`failed` 这些终态 run 的运行历史（`tasks`、插件 checkpoint 表、`plugin_task_completions` 与 `runs` 行）；`stopped` 会保留给下次启动恢复，原始结果与长期元数据不动。若某个插件的 checkpoint 表未登记，脚本会直接报错并拒绝删除，需先用对应版本的服务端插件初始化运行时。

### 6.5 生成服务端交付包

除了一键部署（在源码目录里就地生成 `runtime/`），还可以打一个**自包含的服务端包**用于交付：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\build_server_package.ps1 `
    -PackageVersion 0.4.0 `
    -DatasetDir \\share\dataset -DatasetVersion d2 `
    -UseSystemPython -IncludePostgresRuntime
```

常用参数：`-OutDir`（默认 `dist\server-<PackageVersion>`）、`-BinDir`、`-Config`（默认 Release）、`-DbConn`、`-ResultDbConn`、`-StpResultTable`、`-ServerPort`/`-ManagementPort`、`-SkipDataset`、`-IncludeSymbols`、`-IncludePostgresRuntime`、`-PgBinDir`、`-PythonRuntimeDir`、`-AnalysisWheelhouseDir`、`-UseSystemPython`、`-VCRuntimeDir`。

包内布局与要点：

- `bin/`、`config/`、`tools/`、`scripts/`、`data/`、`result_service/`、`docs/`，以及 `start_server.bat` 与 `release-manifest.json`（逐文件清单）。
- 默认携带独立 Python 与 psycopg；`-UseSystemPython` 才依赖目标机 Python。分析依赖需要预先准备的 wheelhouse。
- 结果服务配置与制品库落在包的 `config/result_service.json` 与 `data/artifacts`，日志在 `data/logs`。
- 服务端插件安装与客户端部署是两条独立路径：含 `server_plugin.json` 的服务端插件 ZIP 通过 `POST /api/server-plugins/preview` 预览、再 `POST /api/server-plugins/install` 安装（需要两个配置 revision 与 `operator_id`）；安装独立落在 `artifact_store_dir/server-plugins/installations`，**不会**加载 DLL、执行包内 Python 或重启服务，安装后需重启调度器与结果服务。新插件默认关闭，升级保留既有设置与已有数据集 manifest。

## 7. 失败处理与恢复边界

| 现象 | 判断 | 处理 |
| --- | --- | --- |
| 客户端在列表中消失 | 超过 `server.client_timeout_ms` 未收到心跳 | 检查客户端进程与网络；客户端重启后重新注册即可领取未完成任务 |
| run 停在 `planning` | 进程在激活屏障前崩溃 | 重启调度器会把它关闭为 `interrupted`，重新提交 |
| 启动时报"恢复受阻" | 保存的 run 与当前插件配置/manifest 不一致，或 checkpoint/部署身份读取失败 | 恢复原部署后重启；不要删除进度 |
| queued run 长时间 `blocked` | 执行指纹与当前部署不一致 | 恢复原部署，或按提示取消该排队 run |
| 部署停在 `waiting_runs` | 旧批次仍未结束 | 在部署页面查看阻塞 run；等待完成，或对 `stopped` 批次执行"恢复/放弃" |
| 客户端报告 `failed` | 该修订被锁存，不会自动重试 | 发布新修订；必要时先清理该客户端的制品缓存（见 [基础客户端与批量部署](基础客户端与批量部署.md)） |
| 结果服务起不来 | 端口占用或配置不可读 | 查 `runtime/logs`；`stop_result_service.bat` 后重启 |
| 数据库连不上 | 实例未启动或口令错误 | 一键部署托管的实例随 `start_server.bat` 启动；独立实例按第 5 节检查 |
