# TestTracking 内网部署与运行

## 1. 适用范围

本文说明 Windows 内网环境中的构建和运行。一键部署可选择 coverage 或 stpcompare 客户端；两类客户端可分别打包并连接同一服务端。每个客户端的生效配置必须恰好启用一个插件，由 Agent 管理一个 Worker 子进程，并保留异常恢复和自动更新。

首次完整部署后，可通过网页分发客户端插件、业务程序和数据集。制品结构、期望配置和双程序示例见 [自动部署使用指南](自动部署使用指南.md)。该机制不替代服务端插件安装，也不支持调度器插件热加载。

生产恢复路径使用 PostgreSQL。部署前应准备独立业务用户、认证密码和明确的客户端网段。仓库 `offline_deploy.json` 中的 `postgres + trust + 0.0.0.0/0` 只适合隔离测试环境。

## 2. 目录和工具准备

从源码构建的机器需要（运行打包后的程序不需要这些开发工具）：

- Visual Studio 2022，安装“使用 C++ 的桌面开发”。
- CMake 3.16 或更高版本，并加入 `PATH`。
- 完整项目目录，包括 `third_party`、`third_party_src/downloads` 和 `tools`。
- PostgreSQL 运行文件。离线部署脚本会从项目附带的 PostgreSQL 包准备本地实例。

示例目录：

```text
D:\WorkSpace\TestTracking
```

仅复制 Git 跟踪文件时，应另外确认第三方二进制和 PostgreSQL 离线包已经带入目标环境。

发布包面向 Windows 10/11 x64 和相应 Windows Server，使用 Release 构建。
两种包均携带 VC++ x64 运行库；构建时自动从 VS redist 目录获取，也可用
`-VCRuntimeDir` 显式提供。服务端默认还携带独立 Python 3.12 和 psycopg 数据库驱动，
目标机无需安装 Python、VS、CMake 或访问源码目录。首次准备 Python 缓存需要联网：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\build_server_package.ps1 `
    -BinDir .\build\offline_verify\bin\Release `
    -Config Release `
    -ResultDbConn 'host=127.0.0.1 port=5432 dbname=testtracking user=testtracking_reader' `
    -StpResultTable stp_compare_old
```

离线构建可提前执行 `python tools/prepare_python_runtime.py --out runtime/python`，
将该缓存随构建材料带入；也可用 `-PythonRuntimeDir` 指定已准备的嵌入式 Python
目录（必须包含 psycopg[binary]，不能是依赖原安装路径的 venv）。只有显式使用
`-UseSystemPython` 才依赖目标机的 `PYTHON` 环境变量或系统 Python。

较完整的分析脚本使用固定版本的 `numpy`、`pandas`、`openpyxl`、`matplotlib`
和 `plotly`。在有网机器执行一次：

```powershell
python -B .\tools\prepare_python_analysis_wheelhouse.py
```

会生成 `runtime\python-analysis-wheelhouse`，其中包含 Windows x64 / CPython 3.12
的 wheel、独立 `pip.pyz` 和 SHA-256 清单。它与 `runtime\python` 一起复制到内网后执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\install_python_analysis_offline.ps1
```

安装过程使用 `--no-index`，不会访问 PyPI。脚本校验 wheel 清单、精确版本和五个主库的
实际导入，然后写入 `runtime\python\analysis-runtime-manifest.json`。服务端包构建脚本会在
发现 wheelhouse 时自动携带并安装这组依赖，包内也保留安装器用于修复或重装。

数据库连接、服务端地址及每台客户端的 worker_id 属于部署配置。PostgreSQL 可用
现有实例，也可加 `-IncludePostgresRuntime` 携带 bin/lib/share 和初始化脚本；不会
复制开发机数据库。AI 使用目标机当前用户配置的 DSH；未选运行或数据库未配置也能提问。

DSH 的程序本体可完全离线安装；模型推理仍依赖内网 OpenAI 兼容接口。把
`TestTracking` 和 `dsh-offline-bundle\dist` 一起复制后，可用同一个入口安装两套依赖：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_dependencies.ps1 `
    -DshBundleDir '..\dsh-inter\dsh-offline-bundle\dist' `
    -LlmBaseUrl 'http://192.168.1.20:8000/v1' `
    -LlmModel 'deepseek-r1'
```

该脚本不调用 npm 或 PyPI，默认只配置 DSH、不常驻启动；主界面的 DSH 原生助手会按需启动
它。服务端结果服务与 DSH 必须由同一个 Windows 账号运行，才能读取该账号的
`%USERPROFILE%\.dsh` 模型配置和会话。
默认 CLI 安装到 `%LOCALAPPDATA%\dsh\dsh.cmd`，主界面会自动发现；如使用
`-DshInstallDir` 自定义安装位置，还需在结果服务配置中将 `providers.dsh.command`
设为该目录下 `dsh.cmd` 的绝对路径。DSH 监听本机回环地址，远程浏览器通过主界面的
同源代理访问，无需把 DSH 的内部端口开放到局域网。

`dist` 保存生成的分发包，可从源码和运行材料重新生成；历史 smoke/test 包可在
确认未运行、未保存独有数据后删除。`runtime` 还可能保存数据集、Python 缓存及
PostgreSQL 数据，不能把它整体当临时文件删除。

## 3. 部署配置

集中配置文件为：

```text
tools\offline_deploy.json
```

主要字段：

| 字段 | 说明 |
| --- | --- |
| `build_config` | 发布包使用 Release；Debug 仅用于源码调试 |
| `server_ip` | scheduler 对客户端可达的 IPv4；空值时脚本尝试自动探测 |
| `server_port` | ROUTER 端口 |
| `management_port` | 调度管理端口，默认 5556，仅本机回环地址监听 |
| `result_port` | 浏览器界面端口，默认 56330，局域网可访问 |
| `db_port`、`db_name` | PostgreSQL 端口和数据库名 |
| `db_user`、`db_password` | 数据库业务账号 |
| `db_auth_method` | PostgreSQL host 认证方式，正式环境建议 `scram-sha-256` |
| `client_cidr` | 允许访问数据库的客户端网段，应写具体 CIDR |
| `dataset_dir`、`dataset_version` | STP 数据集源目录和版本 |
| `step_test_exe`、`program_version` | coverage 被测程序和版本 |
| `plugin`、`baseline_converter_exe`、`candidate_converter_exe` | 客户端类型和 stpcompare 新旧程序 |
| `baseline_program_version`、`candidate_program_version` | stpcompare 新旧程序版本 |
| `dsh_command` | 可选的 DSH CLI 路径；空值时自动发现本机已安装命令 |
| `engine_src_dir` | 可选引擎源码目录 |
| `opencppcoverage_dir` | OpenCppCoverage 目录 |
| `engine_dlls` | 参与覆盖率统计的 DLL 名称 |
| `package_out_dir` | 客户端包输出目录 |
| `worker_id` | 客户端 identity；每台并发客户端必须不同 |
| `task_threads`、`task_size` | 客户端并发槽和服务端任务分组大小 |
| `store_cov` | 是否保留原始 cov 供后续合并 |

同一客户端重装或异常重启时保留它原有的 `worker_id`。复制客户端包到多台机器时，需要在每台机器的 `config/client.json` 中设置唯一值。

coverage 与 stpcompare 的业务程序属于客户端部署输入，不属于服务端框架。它们都可在
内网拿到正式程序后再打包：coverage 使用 `build_package.ps1 -StepTestExe` 和
`-OpenCppCoverageDir`，stpcompare 使用 `-Plugin stpcompare -BaselineConverterExe`
和 `-CandidateConverterExe`。生成后的
`config\client.json` 只保存包内相对路径，换机器或换盘符不需要修改。若业务程序还依赖
非 DLL 的配置文件或资源子目录，应把这些资源显式放入客户端包的
`testenv\program` 并在断网目标机执行一次真实样例；打包器只能自动识别程序同目录的 DLL/PDB。
首次部署可让每个客户端包携带完整 `testenv\dataset`；后续也可通过制品仓库下载完整数据集
到客户端本地缓存。任务执行期间不读取服务器共享目录。服务端保留相同数据集的 manifest 用于生成任务；发布时保持各端的 manifest、
`dataset_version` 和对应程序版本一致，每台客户端只单独设置自己的 `worker_id`。
新生成的 manifest 是 JSONL，每个 STP 条目包含相对路径、`size_bytes` 和
`content_sha256`。运行计划将大小和 SHA-256 一并写入数据库；旧的 `path,size` manifest
仍可读取，但对应历史记录的内容摘要为空。
自动部署使用 HTTP 拉取不可变制品并校验 SHA-256，下载和校验完成后才尝试切换客户端。
当前按完整制品分发，不是共享目录挂载，也不是 STP 文件增量同步。

## 4. 源码内网一键部署

在项目根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1
```

脚本按配置完成 Release 构建、PostgreSQL 初始化、数据集和 manifest 准备、调度器和网页配置生成、所选客户端打包，以及 Python 分析依赖的离线安装。默认输出包括：

```text
build\offline_verify\bin\<Config>\
runtime\dataset\
runtime\scheduler.json
runtime\result_service.json
runtime\logs\
runtime\start_server.bat
runtime\start_result_service.bat
runtime\stop_result_service.bat
dist\client_package\
```

常用开关：

```powershell
# 已有构建和数据库，只更新后续步骤
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1 `
    -SkipBuild -SkipDatabase -SkipFirewall

# Release 构建
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1 -Config Release

# 选择 STP 对比客户端
powershell -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1 `
    -Plugin stpcompare `
    -BaselineConverterExe 'D:\Program\Old\Converter.exe' `
    -CandidateConverterExe 'D:\Program\New\Converter.exe'
```

复制源码时须同时携带 `runtime/python` 和 `runtime/python-analysis-wheelhouse`。
安装过程只读取本地 wheel，不会联网下载。已安装好依赖时可用 `-SkipPythonAnalysis`。
`-SkipPackage` 生成 `runtime/client.template.json`，供配置页编辑；该模板关闭模拟执行，
需按实际业务程序和全量数据位置修改后再使用。普通配置编辑区修改的是输出客户端包内
`config/client.json`；向远程客户端发布更新需使用“插件与部署”中的“制品库”和“客户端部署”页签。

脚本当前不会验证客户端包中的每个运行时 DLL 和业务 DLL 是否齐全。拷贝前应在输出目录运行一次客户端启动检查。

## 5. stpcompare 客户端打包

也可使用构建产物单独生成 stpcompare 客户端包：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\build_package.ps1 `
    -BinDir .\build\offline_verify\bin\Release `
    -Plugin stpcompare `
    -BaselineConverterExe 'D:\Program\Old\Converter.exe' `
    -CandidateConverterExe 'D:\Program\New\Converter.exe' `
    -BaselineProgramVersion 'old-1.0' `
    -CandidateProgramVersion 'new-2.0' `
    -DatasetDir 'D:\Data\STP' `
    -OutDir 'D:\Packages\stpcompare-client' `
    -ServerIp '192.168.1.10' `
    -WorkerId 'compare-worker-01' `
    -DbUser 'testtracking_writer' `
    -DbPassword '<password>'
```

检查生成的 `config/client.json`：只启用 stpcompare，并让 `table` 与 `settle_stpcompare.ps1 -Table` 一致。

两个打包脚本默认只读取一键部署使用的 `build\offline_verify\bin\Release`。
使用其他构建目录时必须显式传入本次构建的 `-BinDir`；不会自动退回历史 `build\rt`。
已有客户端包使用 `-OnlyClient` 更新时，会完整保留原 `config/client.json`，只有显式传入的
部署参数才覆盖对应字段。未传 `-Plugin` 时保留插件选择；显式传入时仅改变启用选择并保留
各插件已有配置。每台机器的 `worker_id`、线程数、数据库连接和自定义参数因此可持续保留。

## 6. 启动

源码一键部署完成后，运行 `runtime/start_server.bat` 同时启动调度器和网页，
本机访问 `http://127.0.0.1:56330/`，其他机器访问 `http://<服务器IP>:56330/`。
`runtime/start_scheduler.bat` 兼容旧入口，行为相同。调度器退出后网页继续运行，结果分析
只使用数据库。需要单独启动或停止网页时，使用 `start_result_service.bat` 或
`stop_result_service.bat`。`result_port` 修改后需重新执行部署或编辑配置并重启网页。
源码启动脚本会验证网页健康状态，将日志写入 `runtime/logs`；AI 默认工作目录为源码根目录。
实际调度配置保存在 `runtime/scheduler.json`，重新编译 Release 只更新程序和构建模板，
不会覆盖数据库、端口或数据集设置。网页配置和启动脚本均指向这份运行配置。
联合启动入口会检查一键部署初始化的准确 PostgreSQL 数据目录，未运行时用本地 `pg_ctl`
启动它，因此没有安装 Windows 服务也能在重启机器后使用。`-SkipDatabase` 部署不托管
数据库启动，现有数据库由管理员自行启动。单独网页启动不会改变数据库生命周期。

服务器包默认通过 `server.log_file=data/logs/scheduler.log` 追加调度日志，一键源码部署写入
`runtime/logs/scheduler.log`。相对日志路径以运行工作目录为基准，父目录会自动创建；控制台
输出和 stdin 命令仍可使用。每条日志即时刷新到文件，重启继续追加。

服务端可使用部署脚本生成的批处理，也可手动运行：

```powershell
Set-Location .\build\offline_verify\bin\Release
.\scheduler.exe .\config\scheduler.json
```

上面的手动命令使用构建模板；源码一键部署请优先运行 `runtime/start_server.bat`。
需要手动调用时，将参数替换为项目内 `runtime/scheduler.json` 的完整路径。

常用控制台命令：

```text
run coverage d1
run stpcompare d1
clients
stop coverage
wakeup coverage
quit
```

`run` 命令先创建 `planning` 记录并生成任务计划。计划成功后，新 run 才激活为 `running`，同时取消同插件的旧 `stopped` run；计划失败不会丢弃旧 run 的可恢复进度。

客户端将完整包复制到目标机后运行：

```text
start_client.bat
```

客户端与 scheduler 必须使用相同的框架协议版本。注册握手会校验协议版本和必需能力；不兼容时 scheduler 不创建 session，并在双方日志中记录 `incompatible ... protocol`。升级时应先停止旧客户端，再替换 scheduler 和全部客户端二进制，最后重新启动，避免滚动升级期间反复注册失败。

启动后在 scheduler 执行 `clients`，确认预期的 `worker_id`、插件类型和版本都已注册。

启用自动部署时，在每台机器的基础 `config/client.json` 中设置唯一的
`client.worker_id` 和可达的 `client.deployment_endpoint`（例如 `http://192.168.1.10:56330`）。
这两个字段不能通过远程期望配置修改。`client.execution_windows` 控制新任务请求，
`client.update_windows` 控制制品下载和激活；两者互相独立，空数组表示全天允许。
窗口使用客户端本机时间，关闭执行窗口时，已开始的任务和结果上报继续完成。

调度器和制品部署均使用基础 `worker_id`，例如 `worker-01`。客户端只启用一个插件，
切换时在同一份部署 patch 中显式关闭旧插件并启用新插件；合并后的生效配置必须仍然
恰好启用一个插件。服务端可以同时向不同客户端分派不同插件的任务。

## 7. 异常恢复操作

### 7.1 scheduler 异常退出

1. 先确认 PostgreSQL 可连接，避免把暂时读取失败当成不可恢复记录。
2. 使用原 scheduler 配置和插件版本重启。
3. 检查日志中是否出现 `run restored: <run_id>`。
4. 用 `clients` 确认客户端重新注册。
5. 查询 `runs` 和任务进度，确认原 run 最终进入 `finished`。

如果任务完成记录对账或 run 恢复状态无法写入 PostgreSQL，scheduler 会退出且不会接受新 run。恢复数据库写入后再次启动，原 run 会重新进入恢复流程。

不要在恢复前替换 manifest、数据集版本或插件存储连接。

### 7.2 客户端异常退出

使用原客户端目录和同一个 `worker_id` 重启。超时前重启时，新注册会接管连接并回收旧 session；超时后重启时，服务端已经通过心跳扫描回收旧任务。两种情况下任务都会用新的 attempt 继续。

## 8. coverage 后处理

运行完成后执行：

```powershell
.\tools\settle_coverage.ps1 `
    -RunId '<run_id>' `
    -DbConn 'host=127.0.0.1 port=5432 dbname=testtracking user=testtracking_writer' `
    -Exe '.\build\offline_verify\bin\Release\coverage_settle.exe'
```

默认只生成贪心精简集合。需要合并 cov 时，客户端运行前设置 `store_cov=true`，结算时再传 `-MergeCov` 和 OpenCppCoverage 路径。

查询结果：

```sql
SELECT file FROM coverage_selected
WHERE run_id = '<run_id>'
ORDER BY file;

SELECT total_files, selected_files, cumulative_points,
       covered_lines, total_lines, percent
FROM coverage_run_summary
WHERE run_id = '<run_id>';
```

## 9. stpcompare 后处理

```powershell
.\tools\settle_stpcompare.ps1 `
    -RunId '<run_id>' `
    -Table 'stp_compare_old' `
    -DbConn 'host=127.0.0.1 port=5432 dbname=testtracking user=testtracking_writer' `
    -OutFile '.\stpcompare_report.txt'
```

脚本以长期 manifest 为基准，仅检查每个 STP 是否已成功入库四份原始结果，并报告失败和缺失项。
具体比较由内网环境中的 Python 数据分析脚本实现。当前客户端配置和脚本必须显式使用同一表名。

## 10. 数据清理

`prune_old_runs.ps1` 用于清理终止运行的框架任务、checkpoint 和 completion journal。脚本从 `plugin_checkpoint_tables` 读取各插件通过 `TaskLedger` 登记的 checkpoint 表，不包含内置插件表名映射。长期 manifest、逐文件 outcome、原始结果和派生结果用于后处理与审计，不应随运行时状态一起删除。

升级后先使用新版 runtime 加载需要清理历史数据的服务端插件一次，初始化会自动登记已有 checkpoint 表。登记记录持续保留，之后禁用插件也不影响清理。目标运行所属插件尚未登记时，脚本报错并回滚该运行的清理；不会跳过 checkpoint 后报告成功。清理连接应与插件的 PostgreSQL 数据库及 schema 一致。

清理脚本处理已终止的运行状态（`finished`、`cancelled`、`interrupted`、`failed`）；`stopped` 状态会保留用于下次启动恢复，只有同插件的新 run 完成计划并激活时才转为 `cancelled`。清理前先查询候选 run，并保留数据库备份。

## 11. 常见问题

| 现象 | 检查项 |
| --- | --- |
| 客户端注册被拒绝 | 先检查日志中的协议版本/能力不兼容，再检查程序和数据集 `version.txt` 是否与服务端 expected version 一致 |
| 两台客户端互相掉线 | 是否误用了相同 `worker_id` |
| 客户端退出后任务不回收 | `server.client_timeout_ms` 是否大于 0，心跳是否到达 scheduler |
| scheduler 重启后没有恢复 run | PostgreSQL 中 run 状态、插件 checkpoint 和连接配置是否一致 |
| coverage 后处理拒绝运行 | run 是否 finished，manifest、outcome、points 是否完整 |
| stpcompare 报告全部缺失 | 客户端写入表与脚本 `-Table` 是否一致 |
| 数据库远程连接失败 | PostgreSQL listen、pg_hba、认证方式、CIDR 和防火墙规则 |

已知实现边界见 [已知限制](已知限制.md)。

## 12. 断网交付验收清单

复制进内网前确认以下材料在同一批次中：

- TestTracking 服务端包、coverage 客户端包和 stpcompare 客户端包均来自同一次 Release 构建。
- 服务端包包含 `runtime\python`、`runtime\python-analysis-wheelhouse`、`postgres` 和发布清单。
- DSH dist 包含 Node、完整 `runtime\node_modules`、部署脚本和 `runtime\VERSION.json`。
- 正式 STP 数据、manifest 和 `version.txt` 一致，客户端与 scheduler 的预期版本相同。
- coverage 被测程序、OpenCppCoverage、stpcompare Converter 及其运行时资源已经放入各自客户端包。

在内网至少执行一次真实双机验收：检查内网模型的 `/v1/models`、浏览器主界面、DSH
聊天、两种插件的一个真实任务、数据库入库和 Python 报告；随后分别强制结束并重启
scheduler 与客户端，确认原 run 继续完成。服务器重启后还要确认 PostgreSQL 服务、
scheduler 和结果服务均按部署方案恢复。完成这组验收之前，只能认为发布材料齐全，
不能认为具体业务环境已经验收通过。
