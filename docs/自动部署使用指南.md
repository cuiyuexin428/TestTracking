# 客户端自动部署使用指南

适用于 Windows x64 内网环境。服务器和客户端先安装同一批兼容的完整发布包，随后通过网页分发客户端插件、业务程序和数据集。客户端从服务器 HTTP 制品仓库拉取文件并在本地执行；不需要互联网或共享目录。

左侧入口为“插件与部署”，页面按四个页签组织：

| 页签 | 用途 | 常用入口 |
| --- | --- | --- |
| 插件 | 查看任务执行插件和数据库分析能力，安装服务端插件包 | 插件详情、安装插件 |
| 制品库 | 上传、搜索和按类型筛选插件、业务程序、数据集 | 上传制品、制品详情 |
| 客户端部署 | 配置单台客户端，查看当前部署、目标部署及应用状态 | 创建部署、编辑、详情 |
| 服务配置 | 编辑调度服务、结果服务与 DSH、本机客户端配置或模板 | 常用表单、保存配置 |

列表只展示主要状态；插件、制品和部署的完整信息在详情抽屉中查看。制品详情可复制完整 SHA-256。服务端安装文件清单、配置 JSON 和字段说明默认收在可展开的详情中。

## 1. 首次准备

每台机器的基础 `config/client.json` 设置独立身份和网页服务地址：

```json
{
  "client": {
    "worker_id": "worker-01",
    "deployment_endpoint": "http://192.168.1.10:56330",
    "deployment_poll_seconds": 30,
    "execution_windows": [],
    "update_windows": []
  }
}
```

这是基础配置中的 `client` 部分，需保留原文件中的 scheduler、插件和数据库配置。`worker_id` 和 `deployment_endpoint` 只能在目标机基础配置中修改，远程 `config_patch` 不允许覆盖它们。端点为空时不启用自动部署。

每个客户端至少启用一个业务插件，可将 coverage、stpcompare 同时设置为 `enabled=true`。Agent 为每个插件管理独立 Worker 子进程，插件可以同时执行；一个子进程异常不终止其他插件。部署使用基础 `worker_id`，多插件调度身份为 `worker_id/插件配置键`，单插件继续使用基础身份。客户端页面按物理机器分组显示各插件状态。

服务端必须已安装相应调度插件、配置数据库和数据集 manifest。含 `server_plugin.json` 的完整服务端插件 ZIP，先上传到“制品库”，再从“插件”页签点击“安装插件”，在展开的“安装服务端插件包”中预览并安装，详见[服务端插件包格式](服务端插件包格式.md)。普通客户端插件 DLL 或 ZIP 仍只用于客户端分发。安装不会自动重启进程，也不会自动启用新插件；升级框架协议仍需更换兼容的完整服务端和客户端程序。

服务端插件制品使用 `kind=plugin`、名称 `<plugin>-server`，上传版本与包内声明一致。安装会验证配置 revision、核对该插件没有正在执行、排队或待恢复的运行，再将 DLL 和配套资源写入新的独立安装目录，并为视图、结果适配器、AI 背景、报告模板建立完整资源快照。升级保留既有插件配置；包内 manifest 仅在没有既有 `stp_manifest` 时提供默认值。配置提交有备份及事务恢复记录，失败会保留或恢复原配置，异常退出后会核对并恢复未完成的配置切换。已有 DLL、其他插件资源和用户保存的分析脚本不会被原地覆盖。

本次 `TaskPlugin::validateRunParameters` 是 C++ 插件接口变更，服务端与所有插件必须同批
重新编译部署。升级前先完成原版本的未完成运行；如需异常恢复，应先使用原 DLL、
manifest 和配置恢复原运行，不能混换 DLL 后直接继续。

## 2. 准备与上传制品

进入“插件与部署 → 制品库”，点击“上传制品”，按类型、名称、版本上传文件。相同类型、名称和版本对应的内容不可更换；内容变化应发布新版本。SHA-256 校验用于确认传输内容一致。制品可为 ZIP 或普通文件，包含多个文件的程序和数据集应使用 ZIP。上传后可按名称、版本或文件名搜索，也可按类型筛选；点击“详情”查看完整文件信息。

推荐名称与压缩包结构如下。下面列出的文件直接位于 ZIP 根目录，不额外套一层目录；如果自行增加目录，配置中的路径也要包含它。

| 类型 / 名称 | ZIP 根目录内容 | 网页自动分配的槽位 |
| --- | --- | --- |
| plugin / coverage | `coverage.dll`、所需依赖、`AI_CONTEXT.md` | `plugin.coverage` |
| program / coverage-tool | `StepTest.exe`、DLL/PDB、资源目录、`version.txt` | `program.coverage-tool` |
| program / opencppcoverage | `OpenCppCoverage.exe` 及完整配套文件 | `program.opencppcoverage` |
| plugin / stpcompare | `stpcompare.dll`、所需依赖、`AI_CONTEXT.md` | `plugin.stpcompare` |
| program / stp-baseline | `BaselineConverter.exe`、依赖、`version.txt` | `program.stp-baseline` |
| program / stp-candidate | `CandidateConverter.exe`、依赖、`version.txt` | `program.stp-candidate` |
| dataset / stp | `version.txt`、`manifest.txt`、原目录结构下的全部 `.stp` | `dataset.stp` |

普通文件上传后位于该制品内容目录的原文件名下。高级编辑区勾选制品时默认使用 `类型.名称` 作为槽位；使用以下 JSON 示例时应选用表中名称。表单向导按插件、程序角色和数据分配槽位，可选择其他名称的制品，同一槽位一次只引用一个版本。STP 新老程序可选同名程序的不同版本，向导分别分配 baseline、candidate 槽位。

客户端将原始制品缓存到 `deployments/objects/<内容SHA256>/archive`；ZIP 解压内容位于同目录的 `content/`。普通文件按内容摘要和文件名共同生成独立目录 `deployments/objects/raw/<联合SHA256>/content/`，因此相同字节的不同文件名可以共存，原始下载仍按内容去重。配置中统一使用 `{artifact:槽位}`，无需手工拼接缓存路径。

数据集 `version.txt` 可写 `d1`。手工部署到机器本地路径的程序仍可用 `version.txt`，例如 coverage 写 `coverage-1.0`，新旧转换器分别写 `baseline-1.0`、`candidate-2.0`。通过制品路径引用的内置插件程序会在预览和发布时自动生成 `sha256:...` 注册版本，以制品内容和执行配置为准，不使用上传页面的人类版本标签。发布后不要在客户端缓存中原地修改文件。

使用正式数据生成 JSONL manifest：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\build_dataset_manifest.ps1 `
    -DatasetDir 'D:\Data\STP' -OutFile 'D:\Data\STP\manifest.txt'
```

manifest 记录相对路径、大小和内容 SHA-256。将同一份 manifest 安装到服务端，并令其 `stp_manifest` 指向该文件；`expected_dataset_version` 应与数据包的 `version.txt` 一致。coverage 的 `expected_program_version`，以及 stpcompare 的 `expected_baseline_program_version`、`expected_candidate_program_version`，应与对应客户端实际注册版本一致。向导预览后的“保存服务端匹配配置”可写入本次程序身份，但仅上传或发布数据集不会自动修改服务端的任务 manifest 或预期数据版本。

变更服务端 manifest、插件或预期版本前，先完成当前相关运行，再统一发布；异常恢复期间保持原版本和 manifest。避免服务器已经要求新版本、客户端仍使用旧版本而无法注册。

## 3. 发布客户端期望配置

进入“插件与部署 → 客户端部署”，点击“创建部署”；已有客户端也可从部署状态列表点击“编辑”。表单向导按五步操作：

1. **选择客户端**：选择已连接客户端或填写基础 `worker_id`。点击“下一步”会先读取该客户端的当前部署；也可点击“读取当前部署”主动重载。
2. **选择插件**：勾选需要同时启用的插件，再用“正在配置的插件”切换 coverage、stpcompare，分别指定插件制品及 DLL 路径，或沿用现有插件。
3. **程序与数据**：选择程序和数据制品，填写包内路径。coverage 配置被执行程序、覆盖率采集工具及 DLL 列表；stpcompare 分别配置老程序、新程序及各自的参数模板。执行模式可选继承、模拟或真实执行；分发程序制品时必须明确选择模拟或真实，不会自动替用户切换为真实执行。coverage 可勾选“保留原始 cov”，已有 patch 保留原值，新配置默认不保存。
4. **运行安排**：设置任务并发数、任务执行时间窗，以及独立的程序与数据更新时间窗。点击“核对部署”会生成并校验配置预览，通过后进入确认步骤。
5. **确认发布**：核对目标客户端、制品版本、并发数和时间安排，填写变更说明；需要时先保存服务端程序匹配配置，再点击“发布客户端部署”。发布后在部署状态列表跟踪客户端应用结果。

从列表编辑已有内置插件部署时可直接使用回填后的向导。主动点击“读取当前部署”会以已有 JSON 为准读取；如进入高级模式，可在“高级配置”中切换“配置方式”为“表单向导”。自定义插件继续使用高级 JSON 编辑，不强行转换成内置插件表单。

选择制品后填写实际包内相对路径，根目录字段可留空表示制品根目录。不选择制品时可填写机器现有路径。向导保留未涉及的高级配置，按勾选列表启用插件；切换编辑插件不会改变启用列表，也不会丢失另一插件的程序和数据草稿。两插件可共享数据制品，也可选择不同数据制品，向导自动分开冲突的数据槽位。

确认步骤显示配置预览和程序内容身份；展开各程序的“内容已核对”详情可查看执行路径及注册版本。返回前面步骤修改后，应重新核对部署；也可点击“生成配置预览”重新校验。需要同步程序预期版本时点击“保存服务端匹配配置”。修改预期版本要求该插件没有未完成运行，并需在保存后重启调度器。随后确认客户端配置，点击“发布客户端部署”。服务端配置保存与客户端发布是两个明确步骤，不构成多机器一起提交的事务。

“高级配置”默认折叠，展开后可查看生成的 JSON；表单向导模式下 JSON 为只读。切换为“高级 JSON 编辑”后可直接维护 `config_patch`，并到“制品库”勾选所需制品；高级模式从选择客户端直接进入确认发布，不经过内置插件表单步骤。切回向导时会按当前 JSON 和制品选择回填；“从 JSON 回填表单”也可显式重新回填。预览及发布都会规范化内置插件程序的内容身份；发布后显示服务端实际保存的配置。

切换四个页签、收起再打开配置不会清空当前部署草稿。读取当前部署或切换目标客户端会载入该客户端保存的配置，执行前应自行保存需要保留的修改。草稿只保留在当前页面内存中，刷新或关闭页面前应保存或复制出来。部署发布使用读取时的 desired revision，服务端匹配配置使用预览时的 scheduler revision。多人修改导致 HTTP 409 时当前草稿保留，应先复制自己的草稿，再读取最新内容、合并和重新预览，不能仅替换 revision 强行覆盖。

`config_patch` 递归合并到该机器的基础配置；对象按字段合并，数组整体替换。每个 revision 的 patch 应包含该版本需要的完整覆盖项，不会叠加上一版 patch。`{artifact:槽位}` 表示下载并校验后的制品内容目录，后面可以接 `/相对路径`。基础配置中未覆盖的连接、工作目录等设置继续保留；工作目录应位于制品缓存之外。

### coverage 示例

勾选 `plugin.coverage`、`program.coverage-tool`、`program.opencppcoverage` 和 `dataset.stp` 对应制品。以下 JSON 可复制到配置覆盖框，按实际 DLL 列表调整 `engine_dlls`：

```json
{
  "plugins": {
    "coverage": {
      "enabled": true,
      "dry_run": false,
      "store_cov": false,
      "dll": "{artifact:plugin.coverage}/coverage.dll",
      "program_dir": "{artifact:program.coverage-tool}",
      "target_exe": "{artifact:program.coverage-tool}/StepTest.exe",
      "opencppcoverage": "{artifact:program.opencppcoverage}/OpenCppCoverage.exe",
      "engine_dlls": [
        "{artifact:program.coverage-tool}/TKernel.dll",
        "{artifact:program.coverage-tool}/TKBRep.dll"
      ],
      "stp_root": "{artifact:dataset.stp}",
      "export_dir": "reports/coverage"
    },
    "stpcompare": { "enabled": false }
  }
}
```

该示例的 `target_exe` 引用了程序制品，预览和发布时服务端会补入内容派生的 `program_version`。coverage 优先使用非空 `program_version`；手工本地程序未设置该值时，仍读取 `program_dir/version.txt`。数据版本继续从 `stp_root/version.txt` 读取。制品页面的版本标签不会自动写入 ZIP 内的 `version.txt`。为准确记录执行配置，制品程序必须显式配置 `dry_run`、`store_cov`、`program_dir`、`opencppcoverage` 和 `engine_dlls`，不能让这些字段隐式继承不同机器的旧配置。

### stpcompare 双程序示例

勾选 `plugin.stpcompare`、`program.stp-baseline`、`program.stp-candidate` 和 `dataset.stp` 对应制品：

```json
{
  "plugins": {
    "coverage": { "enabled": false },
    "stpcompare": {
      "enabled": true,
      "dry_run": false,
      "dll": "{artifact:plugin.stpcompare}/stpcompare.dll",
      "stp_root": "{artifact:dataset.stp}",
      "work_dir": "work/stpcompare",
      "programs": {
        "baseline": {
          "executable": "{artifact:program.stp-baseline}/BaselineConverter.exe",
          "version": "",
          "version_file": "{artifact:program.stp-baseline}/version.txt",
          "arguments": ["--input", "{stp}", "--output-dir", "{outdir}"]
        },
        "candidate": {
          "executable": "{artifact:program.stp-candidate}/CandidateConverter.exe",
          "version": "",
          "version_file": "{artifact:program.stp-candidate}/version.txt",
          "arguments": ["--input", "{stp}", "--output-dir", "{outdir}"]
        }
      }
    }
  }
}
```

该示例的两个 `executable` 都引用了程序制品，预览和发布会分别将 `version` 改为内容派生的身份。机器本地路径仍支持显式 `version`；清空它时读取 `version_file`，未指定版本文件则读取可执行程序旁的 `version.txt`。制品模式必须显式设置 `dry_run` 和各角色的 `arguments`。

两个程序均接收 STP 文件和输出目录参数；插件为 baseline、candidate 分配不同的任务输出目录，每个程序应生成 `info.txt` 与 `info_new.txt`。四份原始结果必须完整、原子入库后该 STP 才成功；后续比较由数据库分析脚本决定。

仅切换插件时，在同一份 patch 中显式关闭旧插件、启用新插件；要同时运行则将两者均启用。`client.task_threads` 控制每个插件的任务并发数，例如启用两个插件且设置 2 时，总任务并发上限约为 4。全局执行时间窗作用于所有插件；部署激活等待所有插件当前任务与结果确认完成后统一切换。

## 4. 两种时间窗与切换过程

两个时间窗可分别配置，例如：

```json
{
  "client": {
    "execution_windows": [
      { "days": [1, 2, 3, 4, 5], "start": "09:00", "end": "18:00" }
    ],
    "update_windows": [
      { "days": [1, 2, 3, 4, 5, 6, 7], "start": "22:00", "end": "07:00" }
    ]
  }
}
```

使用客户端本机时间；`days` 为星期一 1 至星期日 7，跨午夜窗口归属开始的那一天。空数组表示全天允许，开始和结束时间相同表示所选日期全天。执行窗口关闭后不再请求新任务，已经开始的任务和结果重试继续完成。更新窗口不影响查询期望和状态上报。修改更新窗口本身也受当前生效窗口约束，不会通过新的期望配置立即越过旧窗口；配置时应保留足够的维护时段。

更新流程如下：

1. 服务器保存制品选择和配置 patch，生成新的 desired revision。
2. 客户端在更新窗口内下载完整制品、校验 SHA-256、安全解压，生成 `deployments/releases/<revision>/client.json`；旧进程仍可工作。
3. 准备完成后，Agent 停止旧插件进程领取新任务，等待在执行任务及结果上报完成。
4. 确认更新窗口仍开放后，用新配置启动当前插件的 Worker 子进程；成功注册到调度器后，才原子更新 `deployments/active.json` 并上报 ready。
5. 下载或校验失败保持旧版本；新进程启动、注册失败时恢复此前成功配置。失败 revision 不会被自动反复激活，修正后应发布新的 revision。

任务结束时如果更新窗口已关闭，继续使用旧配置，在下个窗口再尝试切换。已缓存制品会复用。网页“已下载”或“应用中”不等于已经可执行，应确认客户端部署“已生效”并检查注册版本。

已生效 revision 收到同一版本迟到的等待窗口、已准备或失败快照时，Agent 保留该版本的
`ready` 状态。若另一期望 revision 部署失败，则继续上报那次失败，不会用旧版本仍可
运行的状态掩盖新版本的部署结果。

需要主动回滚时，编辑该客户端部署，在“确认发布”步骤展开“恢复历史部署”，选择历史版本并点击“恢复此版本”；服务器为历史制品和配置生成新的 revision，客户端仍按上述窗口和切换流程执行。回滚不会删除运行结果或覆盖数据库；服务端 manifest 和预期程序版本也需与回滚版本协调一致。

## 5. 重复任务与多人操作

任务运行按插件类型、服务端插件 DLL 内容摘要、manifest 内容摘要、预期程序版本、数据版本及规范化参数生成身份。同一身份已有活动运行或完整成功记录时默认拒绝重复；`finished` 只表示执行结果已接收，存在业务失败时允许普通重跑，但更早的完整成功记录仍会阻止重复。确需重复已成功的运行时勾选强制重跑并填写原因；也可为业务失败的已结束运行显式记录强制重跑原因。同插件的多次运行进入持久 FIFO 队列。

空字符串、纯空白和空 JSON 对象都表示无运行参数；非空 JSON 对象按稳定键序处理，
其他自定义文本保留原样。参数是否支持由插件决定。coverage 和 stpcompare 当前只接受
空运行参数，非空值会在创建任务前被拒绝；程序参数模板和 `task_size` 请在插件配置中
设置，不能通过填写无效运行参数绕过重复检查。

coverage 与 stpcompare 的制品程序身份由制品 SHA-256、包内执行入口和影响执行的配置派生：STP 包含参数模板与 `dry_run`，coverage 包含程序目录、覆盖率工具、DLL 列表、`store_cov` 与 `dry_run`；其中引用的程序制品依赖也按制品摘要和包内路径记录。相同字节、入口和配置换一个上传版本标签，不会变成新的程序身份。将派生版本保存到服务端对应的 expected 字段并重启后，任务去重沿用已有预期程序版本机制识别它。

包外依赖只记录配置路径，不计算机器上文件的内容；应把影响执行的程序及依赖一起打入程序制品。自定义插件和手工本地路径仍由各插件维护注册版本。数据变化仍需重新生成 manifest，并配置一致的数据版本；该程序身份机制不会替代数据 manifest。coverage 缺少预期程序版本、stpcompare 缺少任一新旧程序版本时，不应依赖去重保护。

当前发布按单个客户端操作；尚无跨客户端批量发布事务、框架 EXE 自更新、大文件断点续传或增量同步。服务端插件安装及匹配配置保存也不自动重启服务，正式切换需统一安排维护时段。

AI 助手仅嵌入服务器上的 DSH 原生界面，不再提供 Codex、自建聊天框或模式切换。DSH 可直接启动，不依赖运行记录、客户端在线状态或数据库可用性。不同浏览器操作身份使用独立原生 Web 进程，原生会话、工作区列表及附件保存在 `runtime/result_service/dsh_web/<operator_id>/`，重新连接沿用该身份的数据，不混入服务器账号原有聊天。后台通过接口读取各插件自己的 `AI_CONTEXT.md`，同一浏览器身份的多个页面共享自己的会话。各会话仍使用同一服务器 Windows 账号的模型配置、凭据和 skills，能看到同一数据库和项目文件，因此会话隔离不等于文件或权限隔离。浏览器身份保存在 localStorage；不同使用者应使用各自浏览器配置文件，不提供登录账号。

DSH 保存分析脚本时先 GET 当前 `source` 和 `revision`，再 PUT 完整 `source`、编辑所依据
的 `revision` 和当前会话 `operator_id`。HTTP 409 表示脚本已被别人修改，应保留草稿、
读取最新脚本并合并后再保存；不能只换成新 revision 重试覆盖。DSH 原生界面
使用此保存约定，成功保存后再运行修改后的脚本。

任务执行和结果分析保持分离：插件保证原始结果入库，Python 报告只读取数据库。仅 coverage 提供默认的精简 STP 集合报告；stpcompare 及其他插件的分析脚本可在内网自行实现、保存和替换。

## 6. 服务配置与草稿

在“服务配置”页签选择“调度服务”“结果服务与 DSH”或“客户端模板”。常用字段显示为表单；未显示的字段可展开“高级配置”编辑完整 JSON，同时查看配置文件位置、字段说明与当前生效值。表单修改会保留未涉及的配置字段，保留 `***` 可沿用已有密钥。

不同配置对象分别保留当前页面内的草稿，切换页签、配置对象或刷新页面数据不会用后台读取结果覆盖已编辑内容。有修改时显示“有未保存修改”，“读取最新配置”暂时禁用；需要舍弃修改时使用“放弃草稿并重载”。遇到保存冲突，先复制草稿，再重载最新配置并合并。浏览器整页刷新或关闭不会持久保存这些草稿。

保存配置后按页面提示重启相应服务。这里的客户端配置或模板只对应服务端配置的本地文件；分发给其他机器应通过“客户端部署”发布，不能仅修改本地模板后等待远程自动更新。
