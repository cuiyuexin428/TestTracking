## 2. 缺陷

### 2.1 提供方超时延迟：已从 P1 撤回，降为"本环境待确认"

> **2026-09-17 修订。** 本节原标题为"P1：提供方超时被固定放大 5 秒（可复现，已定位根因）"。经 Codex 复核（见 [整体审查-codex复核-deepseek-20260917.md](整体审查-codex复核-deepseek-20260917.md)）与我的补充实验，**原定级与根因解释均不成立，在此撤回**。原始实测记录保留在本节末尾，供对照。修订结论以本节开头为准。

**修订后的结论**：**撤回确定 P1 与"改成 `wait()` 即可修复"的建议**。正常环境下该用例通过（Codex R1 实测 0.58 秒 / 三次）；本受限环境存在 `taskkill` 权限失败。**本环境的完整清理状态仍待确认** —— 我方探针有缺陷（见下方二次修订），不足以判定"延迟来自沙箱、不是代码缺陷"。不将其作为发布阻断项。

**推翻原根因的证据**（`build/rt/testtmp/evidence_cleanup.py`，两种场景各一次）：

```text
=== taskkill /T /F (whole tree) ===
  parent pid=5336 grandchild pid=18116  parent_alive=False grandchild_alive=False
  taskkill rc=1 in 0.031s  stderr='ERROR: Access denied'
  after: parent_alive=False grandchild_alive=False
  communicate BLOCKED the full 5.000s
  wait BLOCKED after 5.016s
```

关键在于 `taskkill` **返回码为 1 且 stderr 为 `ERROR: Access denied`** —— 在本沙箱中它没有成功终止进程。我原先把"0.031 秒返回"读作"已杀干净"，实际是"快速失败"。同一实验里 `wait()` 同样阻塞 5 秒，也否证了原文"只用 `wait()` 即可修复"的说法。

> **2026-09-17 二次修订（Codex R3 第 3.1–3.3 节）。** 上述实验本身有三处缺陷，我复核后全部确认，故**该探针不足以支撑"管道为何不关闭"的解释**：
>
> 1. `alive()` 只执行 `tasklist` 并在 stdout 中搜 PID，**不检查 `returncode` 与 stderr**（[evidence_cleanup.py:22-25](../build/rt/testtmp/evidence_cleanup.py#L22)）。查询失败或权限不足都会返回 `False`。日志中 taskkill **之前**就已显示 `parent_alive=False`，却随后 `wait()` 超时 —— 说明该 `False` 不能按"已退出"解释。准确记录应区分**存活 / 已退出 / 无法查询**。
> 2. 探针虽然导入了 `providers`，实际直接调用 `Popen` 与 `taskkill`，**没有走生产清理路径**（`_run_command` / `_stop_process_tree`）。生产实现 [providers.py:173-174](../result_service/app/providers.py#L173) 在 taskkill 之后还有 `if process.poll() is None: process.kill()` 兜底。因此"`wait()` 阻塞 5 秒"只证明**该简化场景**如此，不能直接推广到生产链路。
> 3. PID 文件（[evidence_cleanup.py:29](../build/rt/testtmp/evidence_cleanup.py#L29)）在重跑前未清除，可能读到上一次实验的 PID。
>
> 据此**删除**本节先前"被杀不成的进程留在僵尸状态并持有 stdout 句柄"的表述：证据不足以这样描述，也不应把 Unix 的 zombie 概念套用到 Windows 场景。改为：**终止操作被拒绝已确认；进程终止状态与管道写端持有者仍待可靠探针确认。**
>
> 同理，同一环境下的耗时断言 `${elapsed} < 5` 可能先于子进程检查失败，因此失败报告**不能证明**后续的"子进程已退出"检查已执行。

**原论证的三处错误**（Codex R1 指出，我复核后同意）：

1. 管道 EOF 取决于**写端是否全部关闭**，与"被杀后代持有读端"无关；进程真正退出后句柄由系统回收。
2. 我引用的 `diag_pipes.py` 丢弃了 `taskkill` 输出、使用 `check=False` 且未检查返回码，却直接打印 `kills the tree` —— 该证据不成立。
3. "`communicate` 等 5 秒后 `wait` 又等约 3 秒"这一现象与 8 秒睡眠时长接近，应先确认父进程是否真的被终止，而不能以 `taskkill` 命令快速返回作为判定依据。

**保留的部分**：`_stop_process_tree`（[providers.py:161-174](../result_service/app/providers.py#L161)）调用 `taskkill` 时未检查返回码、未记录 stderr。上文的 `Access denied` 就是这样丢失的。这是**防御性可改进项**，不是已验证缺陷 —— 若要继续定位清理问题，应补齐这一证据，而不是先改耗时。

**下一轮需要的证据**（Codex 提出，我接受）：`taskkill` 返回码与 stderr、清理前后父/子进程存活状态、剩余管道写端的证据。任何修改都应同时验证返回时长与后代退出，不能只改耗时断言。

## 3. 架构决策与边界

### 3.1 整套管理功能无鉴权（决策项，非缺陷）

**位置**：[server.py:84-158](../result_service/app/server.py#L84) 路由、[config.py:38](../result_service/app/config.py#L38) 默认 `host="0.0.0.0"`

无需登录即可通过局域网访问的能力：

| 能力 | 端点 |
| --- | --- |
| 启停 run、唤醒客户端 | `POST /api/scheduler/commands` |
| **在服务器账户下执行任意 Python** | `PUT /api/plugins/{name}/report-script` + `POST .../reports` |
| 以服务器账户调用 codex/dsh CLI | `POST /api/ai/chat`、`POST /api/ai/dsh-web` |
| 改写 scheduler / client / result_service 配置 | `PUT /api/config/{kind}` |

`ManagementServer` 侧把监听限制在 `127.0.0.1` 并校验端点前缀（[ManagementServer.cpp:95-97](../scheduler/src/ManagementServer.cpp#L95)），实现正确。结果服务是该端点的唯一客户端，所以它减少的是**直接网络暴露**，不构成对结果服务使用者的鉴权。

前一份审查已在 [整体审查-20260916.md:148](整体审查-20260916.md#L148) 明确把鉴权排除在范围外，因此这是**有意的取舍，不是遗漏**。

> **2026-09-17 修订（Codex 复核 DS-3.1）。** 原文称 "`Content-Type: application/json` 要求只能算偶然的弱缓解" —— **这句是错的**，我核验后确认：[server.py:401-405](../result_service/app/server.py#L401) 的 `_read_json_body` 只读取 `Content-Length` 后直接 `json.loads`，**不校验 Content-Type**（`Content-Type` 在整个 server.py 中仅作为响应头出现 1 次，`Origin` 出现 0 次）。因此服务端接受任意媒体类型的请求体。

Codex 在隔离的 mock 管理命令上验证：

| 请求 | 响应 | 是否调用模拟管理命令 |
| --- | --- | --- |
| POST，`Origin: http://review.invalid`，`Content-Type: text/plain`，正文为合法 JSON | 200 | 是 |
| POST，同一 Origin，`application/json` | 200 | 是 |
| OPTIONS，声明预检 PUT 与 content-type | 404，无 `Access-Control-Allow-Origin` | 否 |

**结论校正**：服务端确实接受**跨来源的简单 POST 请求形态**（缺 CORS 只限制脚本读取响应，不阻止副作用）。但不能把这一点扩展成"普通外部网页可无条件通过 PUT 改配置或写任意脚本"—— PUT 属非简单请求，需先通过预检，而当前预检不放行（OPTIONS 返回 404）。因此这仍是 P2 加固项，不是无条件可被跨站写。（该验证为 HTTP 层探针，不是跨站浏览器全链路演示。）

**建议**：二选一 —— 在 [已知限制.md](已知限制.md) 中把"无鉴权 + 可被同网段页面触发写操作"写成显式部署前提，或给写操作加共享令牌。就当前"可信内网"约定而言，前者成本更低且一致。

### 8.4 值得肯定的设计

- **"三种状态"在界面上是分开的，不是混为一谈。** 执行状态（run 的 `finished`/`running`）、结果完整性（`result_readiness`）、分析状态是三组独立控件；总览页指标卡明确标注"记录为运行中 —— 非进程在线状态"。这直接对应设计文档"运行已结束、原始数据完整、后处理汇总已生成是三种不同状态"的语义，并且**没有为了让界面好看而合并它们**。
- **可访问性做得比一般内部工具好。** 20 处 `aria-label`、13 处 `role=`、`aria-live="polite"` 用于消息区、`aria-current` 标记当前页、`aria-selected`/`aria-pressed` 标记页签与筛选、拖拽分隔条有 `role="separator"` 与 `aria-orientation`。细节包括 `input[type=search]`、`required`、`title` 与 `aria-label` 成对出现在图标按钮上。
- **错误与空状态有专门通道。** `#system-notice`（`hidden` 控制）、`#report-state`、`#config-dirty` 芯片、`#clients-status`、`#logs-status` 均带 `role="status"`，不是静默失败。
- **报告 iframe 的沙箱是收紧的**：`sandbox="allow-scripts"` 且不带 `allow-same-origin`，报告 HTML 无法访问父页面 DOM、Cookie 或 localStorage。
- **界面文本可缩放**：`A−` / `A+`（`#text-smaller` / `#text-larger`）配合持久化设置，对应前一份审查第 9 项的修复方向。

### 8.5 界面侧的观察与建议

1. **两个 iframe 的沙箱策略不一致（低风险）。** `#report-frame` 有 `sandbox="allow-scripts"`，而 `#dsh-native-frame`（DSH 原生界面）**没有 sandbox 属性**。考虑到它经同源 `/ai/dsh/` 代理、内容是可信的 DSH 应用，风险可接受；但它与报告 iframe 的收紧程度不同，值得在注释里说明为何故意放宽。
2. **`app.js` 单文件 1388 行、约 60 个函数**（已列入第 4 节 rigidity 项）。界面功能已覆盖 6 个页面 + AI 侧栏 + 两个编辑器，状态、协议与 DOM 更新缠在一起；这是本轮新增界面里最需要拆分的一处。
3. **AI 回复的解析依赖正则**（第 4 节已记录）。界面层面看，"AI 生成报告"的产物必须能被 `extractReportScript` 正确切出；建议在应用前做一次语法校验并回显将要保存的脚本摘要，让操作者在落盘前看到实际内容（当前按钮文案是"应用脚本并运行"，直接落盘）。
4. **布局结论需在沙箱外补测。** 我无法验证低分辨率与放大字号下的溢出情况。`style.css` 中侧栏可拖宽（`setPanelWidth` 持久化）、AI 可展开（`setAiExpanded`），但消息区高度分配是否真能收缩，仍需浏览器实测 —— 这正是前一份审查第 9 项修过的区域，属于回归风险点。

## 9. 上一份审查中已失效的发现

复核上一轮（外部）审查的结论，以下三条在本轮代码中**已经修好**，不应再作为待办：

- **`RunStore` 按插件名硬编码 checkpoint 表**。现在表名由插件经 `TaskLedger` 显式传入（`RunStore::init(config, plugin, checkpoint_table)`），并新增 `plugin_checkpoint_tables` 登记表记录 `(plugin_type, checkpoint_table)`，供 `prune_old_runs.ps1` 反查；传入表名还会经过 `IsValidIdentifier` 校验后才拼进 SQL。`common` 中不再出现任何具体插件名。实测 `testtracking` 库中 `plugin_checkpoint_tables` 已有 1 条登记记录，登记与清理链路是通的。
- **`repository.py` 只读设置的时机**。`connection.read_only = True` 现在位于 `psycopg.connect()` 之后、任何事务之前，修掉了"事务已开始才设置、当前事务仍可写"的问题。
- **界面承诺 scheduler 日志落盘**。`scheduler/src/main.cpp` 先探测 `server.log_file` 可写再交给 `Logger::setFile`，不可写时阻止启动。
