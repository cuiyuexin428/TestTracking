# 需求说明

本文说明 TestTracking 当前**已实现**的能力边界。所有条目都能在上位代码或脚本中找到依据；尚未实现的设计一律放在"非目标"一节，不作为现状描述。

- 运行平台前提：Windows x64。服务端与客户端框架、插件、打包脚本、部署代理均按此目标实现（`CMakeLists.txt`、`tools/*.ps1`、`client/`、`scheduler/`）。
- 本文与 [设计说明](设计说明.md)、[开发说明](开发说明.md)、[部署与运行](部署与运行.md) 配套阅读。

## 1. 用户角色

| 角色 | 关注点 | 主要入口 |
| --- | --- | --- |
| 项目维护者 | 框架协议、插件接口、持久化与恢复语义 | 源码、`test/`、`common/inc/common/TaskPlugin.h`、`common/inc/common/WorkerPlugin.h` |
| 插件开发者 | 服务端任务生成、客户端任务执行、结果表与视图 | `plugins/coverage/`、`plugins/stpcompare/`、`plugins/demo/` |
| 部署运维人员 | 离线安装、客户端批量部署、制品与方案发布、失败恢复 | `tools/setup_offline_server.ps1`、结果服务网页 |
| 结果分析人员 | 运行状态、覆盖率精简集合、STP 差异报告、自定义报告脚本 | 结果服务网页（`result_service/app/`） |
| 任务提交者 | 提交 run、选择执行机器、停止/强制重跑 | 结果服务网页 → 调度器管理接口 |

系统**没有登录与权限体系**：结果服务按可信内网使用开放，任何能访问该端口的浏览器都拥有相同操作权限（见 [已知限制](已知限制.md)）。

## 2. 核心闭环

```mermaid
flowchart LR
    DS[数据集 + manifest] --> RUN[提交 run]
    RUN --> DEDUP[工作指纹去重与执行指纹校验]
    DEDUP --> PLAN[服务端插件 plan：写持久任务清单]
    PLAN --> DISPATCH[调度器派发任务给客户端]
    DISPATCH --> EXEC[客户端插件执行 STP]
    EXEC --> DB[("PostgreSQL 原始结果")]
    DB --> POST[独立后处理 / coverage_settle]
    POST --> VIEW[结果服务视图与报告]
```

闭环要求（均已在实现中成立）：

1. **提交**：任务提交者提交 run，框架先做规范化参数处理与工作指纹去重，并保存执行指纹（覆盖已加载插件、插件配置、manifest、数据集版本与参数）。
2. **生成**：服务端插件在自己的 `plan()` 内把任务清单写入自己的持久表；框架只管理待派发/已提交任务的账本。
3. **派发**：调度器按 `plugin_type` 把任务派发到已注册客户端；同一插件同时只有一个 active run（`Storage::ActivateRun` 在 `runs` 表加锁后校验）。
4. **执行**：客户端插件在 `execute()` 内执行外部程序，结果写入 PostgreSQL；`dry_run=true` 时只模拟，不落地业务结果。
5. **入库**：原始结果按文件/任务维度持久化，失败或缺失文件在结果服务中显示为不完整，而不是静默算成功。
6. **后处理**：coverage 由独立工具 `coverage_settle` 计算贪心精简集合；stpcompare 的四份 info 原始结果入库，比较方式由后续分析脚本决定。
7. **呈现**：结果服务只读展示运行、完整性与分析对象，并支持自定义 Python 报告脚本。

## 3. 框架能力

| 能力 | 说明 | 依据 |
| --- | --- | --- |
| 插件双端绑定 | 服务端插件与客户端插件以同一个 `plugin_type` 绑定，框架按该类型路由注册、取任务与上报，业务负载原样透传 | `common/inc/common/TaskPlugin.h`、`common/inc/common/WorkerPlugin.h`、`common/proto/command.proto` |
| 单写者调度 | 网络收发独立线程，所有插件调用与持久化操作在单一 worker 线程上串行执行，FIFO 命令构成生命周期屏障 | `scheduler/inc/scheduler/Scheduler.h` |
| 重复工作防护 | 未完成的等价工作（`queued`/`planning`/`running`/`stopped`，以及"全部任务已上报且退出码为 0"的 `finished`）阻止重复提交；显式强制重跑要求填写原因并关联最近一次等价 run | `scheduler/src/Storage.cpp`、`scheduler/src/Scheduler.cpp` |
| 部署一致性校验 | queued run 在开始规划前校验执行指纹；配置或 manifest 变化时该 run 保持 `blocked` 并给出原因，同插件后续 run 继续 FIFO | `scheduler/src/Scheduler.cpp`、`scheduler/src/SchedulerManagement.cpp` |
| 崩溃恢复 | 调度器重启后未完成 run 可恢复；`planning` 阶段的 run 在启动时统一关闭为 `interrupted`；无法恢复的 run 以显式"恢复受阻"错误停止启动并保留原进度 | `scheduler/src/Storage.cpp`、`scheduler/src/Scheduler.cpp` |
| 客户端恢复 | 客户端在心跳超时前或超时后重启，都可重新注册并领取未完成任务；任务带租约与回执超时，离线客户端的在途任务被回收 | `scheduler/src/Scheduler.cpp`、`scheduler/src/SchedulerMessages.cpp`、`common/proto/command.proto` |
| 增量更新友好 | 运行中的 run 继续使用已加载插件与冻结的任务计划；配置文件修改在重启后生效 | `scheduler/src/Scheduler.cpp` |
| 统一部署协调 | 结果服务持有按插件族的部署目标、制品与滚动更新状态，跨服务重启保持 | `result_service/app/deployment_rollouts.py`、`result_service/app/deployments.py` |

## 4. 插件能力

### 4.1 coverage

- 客户端：调用 OpenCppCoverage 采集业务程序覆盖率；`store_cov` 控制是否保存二进制报告；`program_dir/version.txt` 或 `program_version` 提供程序版本。
- 服务端：按 manifest 生成任务；`expected_program_version`、`expected_dataset_version`、`task_size` 决定注册校验与任务批量。
- 后处理：`coverage_settle`（独立 exe）在事务内计算 `coverage_selected`、`coverage_cumulative_cov` 与 `coverage_run_summary`，`--merge-cov` 时额外合并二进制报告。
- 结果视图：`plugins/coverage/result_view.json` 展示行覆盖率、精简用例数等。

**依据**：`plugins/coverage/src/ClientPlugin.cpp`、`SchedulerPlugin.cpp`、`CoverageStore.cpp`、`CoveragePostProcess.cpp`、`plugins/coverage/src/settle_coverage.cpp`、`tools/settle_coverage.ps1`。

### 4.2 stpcompare

- 客户端：对每份 STP 分别运行 baseline 与 candidate 转换程序，四份 info 原始结果入库；两个程序各自独立目录、独立版本号，参数模板由配置提供。
- 服务端：`expected_baseline_program_version`、`expected_candidate_program_version`、`expected_dataset_version`、`task_size`。
- 比较：由后续分析脚本决定，框架不内置比较语义。
- 结果视图：`plugins/stpcompare/result_view.json`，结果表名由 `plugin_options.stpcompare.result_table` 选择。

**依据**：`plugins/stpcompare/src/ClientPlugin.cpp`、`SchedulerPlugin.cpp`、`StpStore.cpp`、`tools/settle_stpcompare.ps1`。

### 4.3 demo

教学/联调插件，服务端与客户端都有实现，默认在配置中 `enabled: false`，仅用于验证协议与框架行为。

**依据**：`plugins/demo/demo.cpp`、`scheduler/scheduler.json`、`client/client.json`。

## 5. 部署与呈现能力

- **基础客户端与批量部署**：先安装不含插件的基础客户端，再从服务端按方案分配插件、程序与数据；更新只发布方案，客户端更新代理负责下载、校验、暂存，Agent 负责切换与回滚。详见 [基础客户端与批量部署](基础客户端与批量部署.md)。
- **方案与资源管理**：以 profile（可复用方案）+ artifact（不可变制品）+ target（按插件族的部署目标）+ rollout（滚动发布状态机）组织，支持保留旧批次、切换、取消、重试与回滚。详见 [部署方案与资源管理](部署方案与资源管理.md)。
- **结果呈现**：数据库只读渲染 + 可选 Python 报告脚本 + 原生 DSH 助手；调度器等辅助能力通过本机管理端口提供。详见 [设计说明](设计说明.md) 与 [部署与运行](部署与运行.md)。

## 6. 非目标

以下内容当前**没有实现**，不应作为现状使用：

- 跨客户端的批量发布事务；框架 EXE（`client.exe`/`scheduler.exe`）自更新。客户端更新代理只准备插件与业务资源，框架协议升级仍需整体替换兼容的服务端与客户端包。
- 登录、账号、权限隔离。结果服务按可信内网开放；访问控制只有请求校验（同源检查、`Content-Type` 校验）。
- 非 Windows 平台的部署链路。POSIX 分支参与编译，但没有部署目标。
- 具体业务比较算法、报告结论的内置判定。插件只做任务执行与原始结果入库。
- 结果服务对业务结果的写入。结果服务是数据库只读侧车，不写客户端结果。

## 7. 验收视角

一个部署闭环算完成，需要同时满足：

1. `runtime/start_server.bat` 启动后，`http://<服务器IP>:56330/healthz` 与 `/readyz` 返回正常，客户端列表能看到已注册的 Agent 与其插件 Worker。
2. 提交一个 run 后，调度器状态从 `queued` → `planning` → `running` → `finished` 推进，客户端上出现真实执行过程（`dry_run=false`）。
3. 结果服务对应 run 的文件完整性为 complete，报告或视图能读出结果，coverage 的 `coverage_settle` 能产出精简集合。
4. 故障路径可用：客户端 Kill 后重启能重新注册并领任务；调度器重启后未完成 run 可恢复或明确报"恢复受阻"；部署失败被记录为 `failed` 并可重试或回滚。

具体命令、检查点与恢复边界见 [部署与运行](部署与运行.md)、[基础客户端与批量部署](基础客户端与批量部署.md)、[已知限制](已知限制.md)。
