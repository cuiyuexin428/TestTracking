# TestTracking 需求说明

## 1. 目的

TestTracking 用于把一批 STP 文件分发到多个客户端执行，并保存每个文件的原始结果。调度执行与结果分析分开进行：运行期间只处理任务，运行结束后再用独立工具生成覆盖率精简集合或比较报告。

当前版本包含两个业务插件：

| 插件 | 服务端职责 | 客户端职责 | 后处理 |
| --- | --- | --- | --- |
| coverage | 读取 manifest、生成待派发任务并记录完成进度 | 运行 OpenCppCoverage，写入覆盖点和可选 cov | 贪心筛选 STP 集合，可选合并 cov |
| stpcompare | 读取 manifest、生成待派发任务并记录完成进度 | 运行转换程序，写入两份文本结果 | 比较文本并输出差异报告 |

## 2. 设计边界

### 2.1 框架负责

- 客户端注册、会话和心跳。
- run、task、attempt 的生命周期。
- 任务请求、派发、ACK、报告确认和离线回收。
- 服务端异常退出后的运行恢复。
- 插件加载和调用顺序。
- 客户端 Agent 的单 Worker 进程管理、异常恢复和制品自动更新。

每个客户端的生效配置必须恰好启用一个业务插件，调度和部署使用同一个基础 `worker_id`。服务端可以加载多个插件，同时处理来自不同客户端的不同插件任务。通过部署 patch 切换客户端插件时，必须显式关闭旧插件并启用新插件。

单插件内部仍可通过 `client.task_threads` 配置多个执行槽，并行处理同一插件的任务。

### 2.2 插件负责

- 解释业务配置和注册信息。
- 根据 manifest 生成业务任务。
- 执行具体程序并判断单文件结果。
- 持久化插件任务计划、完成日志和原始业务结果。
- 校验客户端报告是否与原任务匹配。

### 2.3 独立工具负责

- 检查一个运行的长期清单和原始结果是否完整。
- 生成 coverage 精简集合、汇总和可选累计 cov。
- 生成 stpcompare 差异报告。

服务端调度插件不读取全部原始结果做筛选，也不生成最终报告。

## 3. 核心运行流程

1. 操作员在 scheduler 中创建指定插件的运行，框架先将 run 保存为 `queued`；同一工作
   指纹已有 `queued`、`planning`、`running`、`stopped` 或完整成功的 `finished` 记录时默认拒绝。
   `finished` 中存在业务失败或缺少成功报告证据时允许普通重跑；更早的完整成功记录仍会阻止重复。
   强制重跑必须填写原因并关联最近的同身份运行，也可关联一次业务失败的已结束运行。
2. 运行轮到执行时转为 `planning`。服务端插件读取 manifest，将文件按 `task_size`
   分组，并持久化不可变任务计划。
3. 计划成功后，框架在同一事务中将新 run 激活为 `running`，并将同插件的旧 `stopped` run 转为 `cancelled`；计划失败时新 run 转为 `failed`，旧 run 保持可恢复。
4. 已注册客户端按空闲执行槽请求任务。
5. scheduler 从对应服务端插件取得任务，为本次派发生成 `attempt_id`，保存派发状态后发送给客户端。
6. 客户端确认收到任务，再由客户端插件逐文件执行。
7. 客户端插件先把原始结果和文件 outcome 写入 PostgreSQL，然后向 scheduler 报告任务摘要。
8. 服务端插件校验摘要并写入任务完成日志；scheduler 再把框架任务标记为已报告。
9. 所有任务结果接收完成后，run 标记为 `finished`；此状态不等于业务全部成功。
   重复判定只依赖框架 `tasks` 的报告状态和退出码，不读取插件业务表。
10. 操作员按需运行独立后处理工具。

运行参数在创建前规范化：空字符串、纯空白和空 JSON 对象等价，非空 JSON 对象按稳定
键序保存，其他自定义文本保持原样。各插件自行验证支持的参数，框架不按内置插件名
硬编码业务参数规则；coverage 和 stpcompare 当前只接受空运行参数。无效参数应在入队
和重复判定前被拒绝。

同一插件的不同运行按 FIFO 持久排队。当前运行完成或人工停止后自动开始下一项；服务端
重启先恢复活动运行，活动运行结束后再启动排队项。不同插件可以在各自的客户端上同时运行；一个客户端只向自身启用的插件请求任务。

任务在各模块之间的具体流动见 [设计说明](设计说明.md)。

## 4. 恢复要求

### 4.1 服务端异常退出

当前交付要求如下：

- scheduler 异常退出后，`runs` 中仍为 `running` 或 `stopped` 的运行在下次启动时恢复。
- 同一插件的新运行先以 `planning` 状态生成计划；只有计划成功并激活为 `running` 时，已有 `stopped` 运行才在同一事务中转为 `cancelled`。
- 新运行计划失败时标记为 `failed`，已有 `stopped` 运行保持不变，仍可在 scheduler 重启后恢复。
- 已写入插件完成日志的任务不重复执行。
- 尚未写入插件 completion journal 的任务重新进入待派发队列。
- 恢复后沿用原 `run_id`，最终仍可进入 `finished`。
- 恢复期间任务对账、run 状态更新或坏记录关闭失败时，scheduler 启动失败；不得在旧 run 未纳入内存调度时接受同插件的新 run。
- 恢复期间 checkpoint、部署身份或 completion journal 的读取失败阻止启动并保留原 run；存储恢复后可重新启动，不因读取故障将 run 标记为 `interrupted`。

该保证以 PostgreSQL 正常可连接、当前 v4 任务计划和完成日志完整为前提。文件存储后端不作为当前生产恢复保证。

### 4.2 客户端异常退出

- 客户端在 `client_timeout_ms` 内重启时，以相同 `worker_id` 注册。scheduler 替换旧 session，并立即回收旧 attempt。
- 客户端超过 `client_timeout_ms` 后重启时，scheduler 先通过心跳超时回收旧 attempt；新 session 再领取任务。
- 被回收的任务使用新的 `attempt_id` 派发；旧 session 的迟到消息不再生效。
- coverage 客户端可以跳过已经完整写入的单文件结果；stpcompare 任务重新派发时可能再次运行转换程序。

同一客户端重启必须保持原 `worker_id`。同时运行的不同客户端必须使用不同的 `worker_id`。心跳超时回收还要求 `server.client_timeout_ms` 大于 0；仓库样例为 5000ms。

## 5. 心跳和通信

- scheduler 使用 ZMQ ROUTER，客户端使用 DEALER。
- 心跳和任务消息共用连接。
- ROUTER 只由服务端网络线程访问；心跳在网络线程快速处理，业务消息交给调度线程。
- `HEARTBEAT_ACK` 只确认当前 session 是否仍登记在服务端。
- 客户端发现 session 失效或长时间收不到服务端消息时重新注册。
- 当前不需要为心跳增加独立 PUB/SUB 通道。

## 6. 插件要求

### 6.1 coverage

- manifest 中的每个 STP 文件都属于本次运行的长期清单。
- `task_size` 控制每个任务包含的文件数，默认值为 25。
- 客户端逐文件运行 OpenCppCoverage，保存覆盖点集合。
- `store_cov=true` 时额外保存原始 cov，供后处理合并。
- 单文件成功或失败都写入 `plugin_file_outcomes`。
- 任务报告只携带文件状态摘要，不携带完整覆盖点。
- `coverage_settle` 只接受已经结束且原始结果完整的运行。
- 精简算法使用确定性的贪心策略，保持相同覆盖点并集，不保证数学上的全局最少文件数。
- 筛选结果写入 `coverage_selected`，汇总写入 `coverage_run_summary`。

### 6.2 stpcompare

- 服务端按相同方式从 manifest 生成任务。
- 客户端为每个文件分别运行 baseline 和 candidate 程序；两者各自在独立目录生成
  `info.txt` 与 `info_new.txt`。
- 四份原始字节按 `(run_id, file, program_role, export_stage)` 原子入库，执行插件不比较内容。
- `settle_stpcompare.ps1` 只检查四份数据的完整性；比较逻辑由独立 Python 分析脚本提供。

## 7. 数据保留

| 数据 | 用途 | 当前策略 |
| --- | --- | --- |
| `runs`、`tasks` | 框架运行状态 | 已完成或不再恢复的运行可按保留期清理 |
| 插件 checkpoint、completion journal | 异常恢复 | 已完成或不再恢复的运行可按保留期清理 |
| `plugin_runs`、`plugin_run_files` | 运行长期清单 | 保留 |
| `plugin_file_outcomes` | 文件最终状态 | 保留 |
| coverage 原始点集和 cov | 重跑后处理、审计 | 保留 |
| coverage 派生表 | 精简集合和汇总 | 同一 run 重跑时替换 |
| stpcompare 原始文本 | 差异分析 | 保留 |

## 8. 验收条件

| 场景 | 验收结果 | 自动化证据或状态 | 前提 |
| --- | --- | --- | --- |
| 正常运行 | 所有任务完成后 run 为 `finished`，文件结果可查询 | `test_runtime_integration` | 服务端和客户端插件版本匹配 |
| 同插件提交不同任务 | 第一项执行、后续项持久排队并按顺序自动开始 | `test_runtime_integration` | PostgreSQL 可写 |
| 服务端重启时存在队列 | 先恢复活动运行，完成后再启动原有 `queued` 运行 | `test_runtime_integration` | 活动运行 checkpoint 完整 |
| 重复任务 | 活动运行或完整成功记录默认阻止重复；仅业务失败时允许普通重跑；有原因的强制重跑创建审计关联 | `test_runtime_integration`、`test_scheduler_protocol`、`test_scheduler_management` | 插件配置稳定的期望程序版本 |
| 并发重复提交 | 两个 scheduler 并发提交只创建一个 run | `test_runtime_integration` | 两个 scheduler 使用同一 PostgreSQL schema |
| 服务端进程被强制结束并重启 | 原 `run_id` 恢复并最终进入 `finished`；有 completion 的任务不重做；其他任务继续执行 | `test_runtime_integration` 真实进程强杀回归 | PostgreSQL 可连接，v4 计划和 completion 完整 |
| `stopped` run 随 scheduler 重启 | 原 `run_id` 恢复并在唤醒后进入 `finished` | `test_runtime_integration` | PostgreSQL 可连接，计划和 completion 完整 |
| 新 run 在规划阶段随 scheduler 异常退出 | 未激活的新 run 转为 `interrupted`，旧 `stopped` run 以原 `run_id` 恢复并完成 | `test_runtime_integration` | 新 run 尚未完成原子激活 |
| 替代 `stopped` run 的新计划失败 | 新 run 为 `failed`，旧 run 仍为 `stopped` 并可在重启后恢复 | `test_runtime_integration` | 失败发生在新 run 激活前 |
| 恢复任务对账写入失败 | scheduler 不进入服务状态；故障解除后原 run 再次恢复并完成 | `test_runtime_integration` | PostgreSQL 恢复为可写后重启 |
| 同插件最新未完成记录不可恢复 | 最新记录转为 `interrupted`，同次启动继续恢复较旧的有效 `stopped` run | `test_runtime_integration` | 较旧 run 的计划和 completion 完整 |
| 客户端在心跳超时前被强制结束并重启 | 超时扫描尚未判离线时，注册接管旧 session；旧 attempt 被回收，新 attempt 完成原任务 | `test_runtime_integration` 固定超时前接管回归 | 重启保持同一 `worker_id` |
| 客户端在心跳超时后重启 | 服务端先判离线并回收，新客户端完成原任务 | 已做专项验证，待固化为独立回归 | `client_timeout_ms > 0` |
| coverage 后处理 | 原始结果完整时写入精简集合；不完整时不发布部分结果 | `test_coverage_settle` | 长期清单、outcome 和 points 完整 |
| stpcompare 后处理 | 报告覆盖完整清单并标出差异和不完整项 | `test_tools_integration` | 客户端与脚本使用同一结果表 |

自动化入口：

```powershell
cmake --build build/rt --config Debug --parallel 8
ctest --test-dir build/rt -C Debug --output-on-failure
```

真实业务程序和完整数据集仍需在部署环境中做一次验收运行。

## 9. 暂缓范围

当前版本不把所有故障组合都作为代码保证，例如旧 checkpoint 自动迁移、文件后端的完整崩溃一致性以及一次性 STOP/WAKE 的状态重放。恢复阶段读取失败的处理见 4.1，其他处理方式和运行规避措施见 [已知限制](已知限制.md)。

单客户端多插件调度延后为低优先级需求。有序插件候选列表、机器统一请求和执行期间保持当前任务类型的方案，在恢复该需求时再讨论；当前不要求客户端自动在多个插件之间选择任务。
