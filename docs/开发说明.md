# TestTracking 开发说明

## 1. 目录结构

```text
TestTracking-02/
├─ common/                 通信协议、插件接口和共享基础组件
├─ scheduler/              服务端网络与调度框架
├─ client/                 客户端状态机与任务执行器
├─ plugins/
│  ├─ coverage/            覆盖率服务端/客户端插件及结算程序
│  ├─ stpcompare/          文本比较服务端/客户端插件
│  └─ demo/                最小插件示例
├─ test/                   单元、协议和真实进程集成测试
├─ tools/                  构建、部署、数据库和后处理脚本
└─ docs/                   当前需求、设计、开发和运行文档
```

服务端和客户端使用同一个插件 DLL，但通过不同导出函数创建 `TaskPlugin` 和
`WorkerPlugin`。一个 scheduler 可以启用多个插件，并服务启用不同插件的不同客户端。
每个客户端的生效配置必须恰好启用一个插件；Agent 管理一个 Worker 子进程，保留异常恢复
和制品自动更新。单客户端多插件调度暂列为低优先级后续需求。

## 2. 构建环境

- CMake 3.16 或更高版本。
- 支持 C++17 的 MSVC 工具链。
- `third_party` 中的 protobuf、ZeroMQ、Abseil、JSON 等依赖。
- PostgreSQL 客户端库和测试所需的 PostgreSQL 二进制。

常用构建命令：

```powershell
cmake -S . -B build/rt
cmake --build build/rt --config Debug --parallel 8
```

Windows 多配置构建的运行文件位于：

```text
build/rt/bin/Debug/
```

其中包括 `scheduler.exe`、`client.exe`、插件 DLL、`coverage_settle.exe` 和运行时 DLL。配置样例复制到相邻的 `config` 目录。

第三方依赖的独立构建见 [tools/README.md](../tools/README.md)。

## 3. 测试

运行全部测试：

```powershell
ctest --test-dir build/rt -C Debug --output-on-failure
```

测试清单以 `test/CMakeLists.txt` 注册为准，本文不记录会随增删漂移的具体数量。主要覆盖范围如下：

| 测试 | 关注点 |
| --- | --- |
| `test_common`、`test_messages`、`test_zmq`、`test_config` | 公共组件和协议基础行为 |
| `test_client_runtime` | 执行线程、取消和进程生命周期 |
| `test_client_protocol` | 客户端注册、请求和报告状态机 |
| `test_scheduler_protocol` | scheduler 会话和任务协议 |
| `test_plugin_runtime` | 共享 TaskLedger、两个插件和文件存储 |
| `test_plugin_runtime_db` | 两个插件的 PostgreSQL 原子发布与重连 |
| `test_coverage_client` | coverage 客户端执行、缓存和失败结果 |
| `test_stpcompare_restore` | stpcompare 任务计划恢复 |
| `test_coverage_settle` | coverage 完整性检查、贪心筛选、事务回滚和 cov 合并 |
| `test_runtime_integration` | 真实 scheduler/client 进程、私有 PostgreSQL 和异常恢复 |
| `test_tools_integration` | PowerShell 工具的主要契约 |
| `test_client_startup` | 客户端启动失败和退出路径 |

涉及 PostgreSQL 的测试创建私有实例或独立 schema，不应连接业务数据库。异常恢复改动至少应运行：

```powershell
ctest --test-dir build/rt -C Debug -R "test_(runtime_integration|plugin_runtime|plugin_runtime_db|stpcompare_restore)" --output-on-failure
```

客户端恢复测试需要分别固定两个时序：心跳超时前重启，以及等待服务端记录 `client offline` 和回收任务后重启。

## 4. 配置

### 4.1 scheduler

样例：[scheduler/scheduler.json](../scheduler/scheduler.json)

| 字段 | 代码默认值 | 说明 |
| --- | --- | --- |
| `server.router_endpoint` | `tcp://*:5555` | ROUTER 监听地址 |
| `server.poll_timeout_ms` | `50` | 网络轮询间隔 |
| `server.client_timeout_ms` | `0` | 客户端离线阈值；`0` 表示不按心跳回收 |
| `server.task_lease_timeout_ms` | `0` | 已 ACK 任务租约；`0` 表示关闭 |
| `server.task_ack_timeout_ms` | `10000` | 未 ACK 派发的回收时间 |
| `server.db_conn` | 空 | 框架状态数据库；生产恢复需要配置 |

`plugins` 下每个对象至少包含 `dll` 和 `enabled`。服务端通过插件对象的键和 `pluginType()` 路由。

### 4.2 client

coverage 样例：[client/client.json](../client/client.json)
stpcompare 样例：[client/client.stpcompare.json](../client/client.stpcompare.json)

| 字段 | 代码默认值 | 说明 |
| --- | --- | --- |
| `scheduler.endpoint` | `tcp://127.0.0.1:5555` | scheduler 地址 |
| `scheduler.poll_timeout_ms` | `50` | 客户端轮询间隔，代码限制在 1 到 100ms |
| `client.worker_id` | `worker-1` | DEALER identity；同一客户端重启保持不变，不同客户端必须唯一 |
| `client.heartbeat_interval_ms` | `1000` | 心跳间隔 |
| `client.task_threads` | `1` | 本地并行任务数 |
| `client.request_backoff_initial_ms` | `200` | 无任务后的初始退避 |
| `client.request_backoff_max_ms` | `30000` | 最大退避 |
| `client.register_timeout_ms` | `5000` | 单次注册等待时间 |
| `client.register_max_attempts` | `5` | 首次启动的注册尝试上限 |
| `client.request_timeout_ms` | `5000` | 请求和服务端会话超时基准 |
| `client.report_retry_ms` | `500` | 未确认报告的重发间隔 |

客户端配置中必须恰好有一个 `enabled=true` 的插件。

### 4.3 coverage 插件

服务端常用字段：

| 字段 | 说明 |
| --- | --- |
| `stp_manifest` | STP 清单路径 |
| `task_size` | 每个任务包含的文件数，默认 25 |
| `expected_program_version` | 允许的程序版本；空值表示不校验 |
| `expected_dataset_version` | 允许的数据版本；空值表示不校验 |
| `store_type`、`db_conn`、`store_dir` | TaskLedger 存储配置；checkpoint 表名由服务端插件传入并由插件维护，PostgreSQL 后端会登记该表供清理工具使用。当前 coverage 使用 `coverage_checkpoints`，stpcompare 使用 `stp_compare_checkpoints` |

客户端常用字段：

| 字段 | 说明 |
| --- | --- |
| `program_dir`、`stp_root` | 程序和数据集目录 |
| `target_exe`、`opencppcoverage` | 被测程序和覆盖率程序 |
| `program_version` | 非空时作为注册程序版本；制品部署自动注入 `sha256:...`，未设置时继续读取 `program_dir/version.txt` |
| `engine_dlls` | 传给 OpenCppCoverage 的模块列表 |
| `export_dir` | 临时报告目录 |
| `process_timeout_ms` | 单文件外部程序超时，默认 300000ms |
| `store_cov` | 是否保存原始 cov |
| `keep_reports` | 是否保留单文件临时报告 |
| `store_type`、`db_conn`、`store_dir` | 原始结果存储；代码默认使用文件后端 |

`dry_run` 代码默认值为 `true`，`dry_run_delay_ms` 默认值为 0，两者用于测试。正式运行需要显式设置 `dry_run=false`。`engine_dlls` 默认是空数组，`store_cov` 和 `keep_reports` 默认是 `false`；非 dry-run 且 `export_dir` 为空时使用 `reports`。

### 4.4 stpcompare 插件

服务端除数据版本外，分别配置 `expected_baseline_program_version` 和
`expected_candidate_program_version`。客户端主要字段为：

| 字段 | 说明 |
| --- | --- |
| `programs.baseline` | 老程序的 `executable`、版本和参数模板 |
| `programs.candidate` | 新程序的 `executable`、版本和参数模板 |
| `arguments` | 默认 `--input {stp} --output-dir {outdir}`；两个占位符都必须存在 |
| `work_dir` | 每次执行的独立工作目录根路径 |
| `process_timeout_ms` | 外部程序超时，默认 300000ms |
| `table` | PostgreSQL 结果表名；部署时应显式配置 |

两个程序在每个 STP 的独立 `baseline`、`candidate` 输出目录运行，且固定生成
`info.txt`、`info_new.txt`。插件将四份原始字节按 `program_role` 和 `export_stage`
写成长表，同时保存 SHA-256、字节数、程序版本和 attempt；它不解析或比较内容。
`work_dir` 默认为 `stp_compare_work`，结果表默认 `stp_compare_results`。

### 4.5 部署配置、程序身份与服务端插件安装

网页部署向导生成单客户端单插件的 `config_patch`，保留未涉及的高级配置，并显式关闭
其他已知插件。执行和更新时间窗分别支持继承基础配置、全天或多段时段；程序制品发布
要求明确 `dry_run`，避免不同客户端继承的旧设置改变执行语义。高级 JSON 模式继续可用。
预览不会更改部署，发布使用读取时的 desired revision；HTTP 409 保留草稿供合并。

`result_service/app/program_bindings.py` 仅为 coverage 与 stpcompare 的制品执行路径派生
程序身份，以程序制品 SHA-256、包内入口和执行配置稳定序列化后生成 `sha256:...`。
coverage 包含程序目录、覆盖率工具、模块列表、`store_cov` 和 `dry_run`；STP 分角色包含参数数组和
`dry_run`。依赖引用程序制品时使用其摘要与包内路径；机器本地依赖只记录路径，不读取
远端文件内容。上传名称、版本标签以及下载后的缓存绝对路径不参与该身份。

预览和保存 desired 都会规范化程序版本：coverage 写入 `program_version`，STP 写入
`programs.<role>.version`。`/api/deployments/bind-scheduler` 使用预览时 scheduler revision
保存同源 expected 字段，在值变化前核对相关插件没有在线或持久化未完成运行，保存后
需要重启调度器。该版本经现有注册校验和运行指纹参与去重，不改变插件拥有结果存储、
结果分析只依赖数据库的边界。本机路径仍可使用原显式版本、`version_file` 或 `version.txt`。

`result_service/app/server_plugins.py` 安装通用服务端插件 ZIP；包格式见
[服务端插件包格式](服务端插件包格式.md)。安装预览只验证包和配置，不加载其中 DLL 或
执行 Python 代码。正式安装核对两份配置 revision 及未完成运行，将包写入新的安装目录，
复制现有配套资源并应用新插件资源，再切换 scheduler/result service 配置引用。备份与
事务记录负责提交失败、异常退出后的恢复，用户分析脚本保留。升级保留既有插件设置；
新插件默认未启用。没有热加载或自动进程重启，也不覆盖框架 EXE。

客户端部署、服务端配置保存及服务端插件安装是分别确认的操作，尚无多客户端批量发布
事务。联调及发布顺序见[自动部署使用指南](自动部署使用指南.md)。

## 5. 插件接口

### 5.1 服务端 `TaskPlugin`

实现位置：[common/inc/common/TaskPlugin.h](../common/inc/common/TaskPlugin.h)

| 方法 | 用途 |
| --- | --- |
| `pluginType` | 返回稳定的路由键 |
| `init` | 读取配置并初始化存储 |
| `validateClient` | 检查客户端业务信息，例如版本 |
| `validateRunParameters` | 创建 run 前校验规范化参数；默认接受，由插件覆写支持的业务规则并返回拒绝原因 |
| `plan` | 生成并持久化本次 run 的任务计划 |
| `requestTask` | 返回一个待派发任务 |
| `processResult` | 校验任务摘要并持久化完成进度 |
| `runFinished` | 判断插件任务是否全部完成 |
| `requeue` | 将被回收的 task 放回待派发队列 |
| `saveCheckpoint`、`restore` | 保存和恢复运行状态 |
| `cancel` | 清理当前内存运行状态 |

框架在调度线程串行调用这些方法。`processResult=false` 当前表示提交没有成功，scheduler 会继续重试该报告。

创建 run 时先规范化 `params`，再调用 `validateRunParameters`，通过后才生成工作指纹并
入队。空字符串、纯空白和空 JSON 对象规范化为空；非空 JSON 对象按稳定键序序列化，
其他自定义文本保留原样。自定义插件可沿用默认接受行为或覆写校验，框架不维护按插件
类型划分的参数白名单。coverage 与 stpcompare 覆写为拒绝非空参数，并在 `plan` 中保留
同样检查；其程序路径、参数模板和任务分组通过插件配置定义。

### 5.2 客户端 `WorkerPlugin`

实现位置：[common/inc/common/WorkerPlugin.h](../common/inc/common/WorkerPlugin.h)

| 方法 | 用途 |
| --- | --- |
| `pluginType` | 与服务端插件匹配的路由键 |
| `init` | 读取本机程序、数据和存储配置 |
| `collectRegistrationInfo` | 生成版本等注册信息 |
| `handleValidationReply` | 处理服务端插件的验证结果 |
| `execute` | 执行一个 Task，先发布原始结果，再返回摘要 |
| `heartbeatInfo` | 提供简短的业务监控文本 |

耗时等待应使用带 `CancellationToken` 的 `execute` 重载，并在发布结果前再次检查取消状态。

### 5.3 DLL 导出

插件 DLL 需要导出四个 C 接口：

```cpp
CreatePlugin
DestroyPlugin
CreateClientPlugin
DestroyClientPlugin
```

修改公共插件接口后，scheduler、client 和全部插件 DLL 需要一起重建。

本次新增 `TaskPlugin::validateRunParameters` 改变了 C++ 虚函数接口，服务端和所有插件
必须同批重新编译部署，不得混用旧 DLL。已有未完成 run 应先在原版本完成；发生异常时
使用原 DLL、manifest 和配置恢复，完成后再升级。新 DLL 的执行指纹不能代替原运行的
恢复身份。

## 6. 新增插件

1. 在 `plugins/<name>` 下定义业务 protobuf、服务端插件和客户端插件。
2. 服务端插件使用 `TaskLedger` 保存不可变计划和完成日志。
3. 客户端插件在返回成功摘要前原子发布逐文件结果。
4. `pluginType()` 在服务端、客户端和配置中保持一致。
5. 在 `plugins/CMakeLists.txt` 加入子目录，并导出四个工厂函数。
6. 增加服务端计划恢复、客户端执行、PostgreSQL 发布和协议集成测试。
7. 如需全局分析，增加独立工具；不要把批量结果扫描放入 scheduler 插件回调。

任务 ID 当前由插件生成，并被框架作为全局键使用。新插件应把 `run_id` 或插件类型纳入 task ID，避免与其他运行冲突；该约束同时记录在 [已知限制](已知限制.md)。

## 7. 持久化和恢复约定

- `Scheduler::Storage` 记录框架 run 和 attempt 状态。
- `TaskLedger::plan` 在任务可派发前保存完整计划。
- `TaskLedger::commit` 先写 completion journal，再更新内存完成集合。
- scheduler 只在插件接受结果后把框架任务标记为 reported。
- 重启恢复以插件计划和 completion journal 为准，不依赖旧进程的 `in_flight` 内存。
- 重启时 scheduler 根据 PostgreSQL completion journal 补齐可能因提交间崩溃而遗漏的 reported 状态。
- 恢复所需 checkpoint、部署身份和 completion journal 无法读取时抛出 `RecoveryBlocked`；scheduler 拒绝启动并保留原 run。查询失败或文件读取失败不得当成“记录不存在”。
- 尚未写入 completion 的任务允许重新执行，因此插件逐文件发布需要幂等。

生产恢复配置应同时为 `server.db_conn` 和插件 `db_conn` 指向可用的 PostgreSQL。详细流程见 [设计说明](设计说明.md)。

## 8. 后处理工具

coverage 筛选：

```powershell
.\tools\settle_coverage.ps1 `
    -RunId '<run_id>' `
    -DbConn 'host=127.0.0.1 port=5432 dbname=testtracking user=postgres' `
    -Exe '.\build\rt\bin\Debug\coverage_settle.exe'
```

查询筛选结果：

```sql
SELECT file
FROM coverage_selected
WHERE run_id = '<run_id>'
ORDER BY file;
```

stpcompare 四份原始结果完整性检查：

```powershell
.\tools\settle_stpcompare.ps1 `
    -RunId '<run_id>' `
    -Table 'stp_compare_old' `
    -DbConn 'host=127.0.0.1 port=5432 dbname=testtracking user=postgres'
```

工具默认值可能随配置变化，自动化调用建议显式传入 run、连接串、表名和程序路径。
