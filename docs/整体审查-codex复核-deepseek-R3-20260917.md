## 3. 新证据仍需准确表述的地方

### 3.1 `alive=False` 不足以证明进程已退出

[evidence_cleanup.py:22–25](../build/rt/testtmp/evidence_cleanup.py#L22) 的实现是执行 `tasklist`，然后仅在 stdout 中查找 PID：

```python
out = subprocess.run([...], capture_output=True, text=True)
return f'"{pid}"' in (out.stdout or "")
```

它没有检查 `returncode` 和 stderr。查询失败、权限不足、空输出都会被当成 `False`。R2 日志中，在 taskkill **之前**父进程已经显示 `parent_alive=False`，但之后对同一 `Popen` 的 `wait()` 超时，这说明这个 False 不能按“已退出”解释。

准确记录应区分“存活 / 已退出 / 无法查询”。当前可以确认两次 taskkill 被拒绝，但无法从这些 False 确认子进程状态，更无法直接确认哪个进程持有输出管道写端。

### 3.2 新探针没有执行完整的生产清理路径

`evidence_cleanup.py` 虽然导入 `providers`，实际场景却直接调用 `Popen` 和 taskkill，没有调用 `_run_command` 或 `_stop_process_tree`。生产实现 [providers.py:173–174](../result_service/app/providers.py#L173) 在 taskkill 后还有：

```python
if process.poll() is None:
    process.kill()
```

所以探针中 `wait()` 等满 5 秒只能说明**该直接 taskkill 场景**下等待仍然阻塞，不能直接证明生产实现加上 fallback 后也会如此。

这不改变“撤回一行修复建议”的结论：R1 的控制实验已经说明 wait 快速返回也不等于子进程完成清理。但后续如定位根因，应观察真实清理链路，包括 taskkill 和 fallback kill 的结果，而不是把简化探针称为生产路径的完整复现。

### 3.3 重复实验还需避免旧 PID 和不可查询状态

探针 [29 行](../build/rt/testtmp/evidence_cleanup.py#L29) 使用固定 PID 文件，重跑前没有清除；[47–51 行](../build/rt/testtmp/evidence_cleanup.py#L47) 只要文件存在就读取，可能读到前一次 PID。下次使用唯一实验目录或确认 PID 文件属于本次启动即可，不必为此扩大产品逻辑。

同类问题也适用于验证用例：`test_ai_providers.py` 的子进程检查在 `OpenProcess` 失败时没有区分“不存在”和“权限拒绝”；受限环境中的耗时断言又可能更早失败，因此失败报告不能证明后续的子进程检查已执行。这属于诊断/测试可靠性改进，不等于已经证明正常环境的清理失败。

原审查修订处还出现“僵尸状态并持有 stdout 句柄”的解释。现有证据不足以这样描述，也不应将 Unix 的 zombie 概念套用到这里。宜写成“终止操作被拒绝，进程终止状态及管道写端持有者尚需可靠探针确认”。

**DS-2.1 最终记录建议：** 原确定 P1 关闭；受限环境已确认 taskkill 权限失败；生产完整清理链路及剩余管道持有者未完成验证。失败诊断可以改进，原有 communicate 不因本轮回应直接改为 wait。
