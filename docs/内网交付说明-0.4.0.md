# TestTracking 0.4.0 内网离线交付说明

目标平台：Windows x64。本次交付包含完整源码及离线依赖、同批 Release 服务端和两个客户端框架包，以及 DSH 离线包。程序版本绑定、部署向导、服务端插件安装、单客户端单插件和仅 DSH 的实现均已纳入。

## 1. 交付内容

| 文件 | 用途 |
| --- | --- |
| `TestTracking-02-source-offline-0.4.0.zip` | 完整项目源码、C++ 第三方库及源码缓存、Python 运行时、分析 wheelhouse；支持内网修改和编译 |
| `TestTracking-server-0.4.0.zip` | 最新 Release 调度器、插件、管理界面、Python 分析服务及 PostgreSQL 运行材料 |
| `TestTracking-client-coverage-framework-0.4.0.zip` | coverage 客户端框架、自动更新工具及配置模板 |
| `TestTracking-client-stpcompare-framework-0.4.0.zip` | stpcompare 客户端框架、自动更新工具及新老程序配置模板 |
| `dsh-offline-bundle-20260916.zip` | 已校验的 DSH、Node.js、前端和离线安装材料，解压根目录为 `dist` |
| `SHA256SUMS.txt`、`verify_delivery.ps1` | 本交付文件完整性清单与校验工具 |

在交付目录运行校验后，再解压到新的工作目录：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\verify_delivery.ps1
```

**两个客户端 ZIP 是框架模板，不包含正式业务 EXE、OpenCppCoverage 和全量 STP 数据。** 服务端包也不含正式 manifest。源码中的样例数据用于测试，不能代替正式数据。

本次 C++ 插件接口有变化，服务端、客户端和插件必须使用兼容的同批构建。未完成运行应先在原 DLL、manifest 和配置下恢复完成，再升级；不要直接覆盖正在运行的数据库和部署目录。

## 2. 在内网编译和配置源码

编译机需要预先安装 Visual Studio 2022 C++ 桌面开发工作负载、Windows SDK 和 CMake；这些工具的离线安装源不在本交付中。运行已构建的服务端和客户端无需安装编译工具。

源码 ZIP 解压后的根目录为 `TestTracking-02`。在该目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\verify_offline_build.ps1 -Config Release
```

默认输出为 `build/offline_verify/bin/Release`。保留 `third_party`、`third_party_src/downloads`、`runtime/python` 和 `runtime/python-analysis-wheelhouse`，离线构建和依赖安装会使用这些目录。

如需从源码配置本机服务器，先编辑 `tools/offline_deploy.json`，填写服务器地址、数据库、正式数据和程序路径，再运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\setup_offline_server.ps1 -Config Release
```

coverage 填写 `step_test_exe`、`opencppcoverage_dir` 等字段。stpcompare 填写 `baseline_converter_exe`、`candidate_converter_exe` 和各自版本；两个程序均接收输入 STP 与输出目录参数，在各自独立输出目录生成 `info.txt` 和 `info_new.txt`。任务阶段保存四份原始内容，比较逻辑由后续分析脚本决定。

## 3. 使用服务端和客户端包

服务端解压后，先配置 `config/scheduler.json`、`config/result_service.json` 中的数据库连接、正式 manifest、数据版本和程序预期版本。可连接已有 PostgreSQL，或使用包内工具初始化新数据库；具体初始化步骤见服务端 README。生产数据需要备份和持续保存，不能使用开发机测试数据库替代。

执行 `start_server.bat` 启动服务，局域网浏览器访问 `http://<服务器IP>:56330/`。此界面面向可信局域网，无登录鉴权。常用端口：

| 端口 | 用途 |
| --- | --- |
| TCP 56330 | 网页、报告、DSH 代理 |
| TCP 5555 | 客户端任务通信 |
| TCP 5432 | PostgreSQL，客户端直接写入结果 |
| TCP 5556 | 调度管理，仅服务器本机使用 |

端口均可配置，防火墙按实际网段和端口放行。分析模块只依赖数据库，scheduler 停止时仍可查看已入库结果和生成报告。

客户端框架模板使用 `127.0.0.1` 作为待配置地址。每台机器必须在 `config/client.json` 中改为实际服务器任务地址、数据库地址和 `client.deployment_endpoint`，并设置唯一 `worker_id`。每个客户端只启用一个插件；不同客户端可以执行不同插件。

补齐客户端程序和数据有两种方式：

1. 在内网使用 `tools/build_package.ps1` 生成完整包，每台客户端拷贝全量数据。例如 STP 使用 `-BaselineConverterExe` 和 `-CandidateConverterExe` 指定两个程序；coverage 使用 `-StepTestExe` 和 `-OpenCppCoverageDir`。
2. 通过主界面上传插件、程序和完整数据制品，用部署向导配置目标客户端。客户端通过服务器 HTTP 地址拉取制品，校验 SHA-256 并复用缓存，不需要互联网或共享目录。

执行窗口与更新窗口独立设置；执行窗口外不领取新任务，已开始的任务允许完成。发布后要核对客户端“已生效”和注册状态，不能只依据“发布成功”。当前逐台发布，没有批量发布事务。

程序制品按内容和执行配置派生版本，向导可保存服务端匹配配置；配置变化后按页面提示重启 scheduler。正式数据对应的 manifest 和预期数据版本仍需配套配置，上传数据不会自动替换服务端 manifest。相同执行身份的已完成任务默认阻止重复提交，必要时可明确选择强制重跑。

服务端插件 ZIP 使用 `server_plugin.json` 契约；可在网页预览和安装 DLL、结果视图、适配器、AI 背景和可选报告模板。安装有配置冲突检查与失败恢复，但不会自动重启服务、启用新插件、更新框架 EXE 或安装额外 Python 依赖。服务端包内 `docs` 提供《自动部署使用指南》《服务端插件包格式》和《已知限制》。

## 4. Python 分析与 DSH

Python 分析依赖已随包提供。需要恢复安装时，在源码或服务端包根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\install_python_analysis_offline.ps1
```

安装使用本地 wheelhouse 和 `--no-index`，不访问 PyPI。内置覆盖率脚本从数据库选择覆盖点相同条件下尽量少、较小的 STP 集合；其他插件的分析脚本由内网使用者编写或借助 AI 生成。每个插件提供自己的 `AI_CONTEXT.md` 说明功能和数据语义。

将 DSH ZIP 解压到源码同级的 `dsh-offline-bundle`，再运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\setup_offline_dependencies.ps1 `
    -DshBundleDir '..\dsh-offline-bundle\dist' `
    -LlmBaseUrl 'http://<内网模型地址>:8000/v1' `
    -LlmModel '<模型ID>'
```

如果模型接口需要密钥，按工具参数配置。DSH 默认安装路径为 `%LOCALAPPDATA%/dsh/dsh.cmd`；自定义路径需设置结果服务 `providers.dsh.command`。结果服务应由配置 DSH 的同一 Windows 账号运行。

当前仅支持 DSH，浏览器使用服务器上的 DSH，每位操作用户有独立会话。主界面代理原生 DSH 页面，无需另开其内部端口。程序可以离线安装，实际聊天需要内网模型接口可达。

## 5. 正式环境验收

正式部署前，使用内网实际业务程序、OpenCppCoverage、全量数据和模型端点验证：任务执行与入库、进度和日志、分析报告、DSH 对话，以及服务端和客户端异常退出后的恢复。

本地模拟业务和模拟模型测试用于验证软件流程，不代表正式程序与模型已验收。数据库、运行配置、自定义分析脚本及 DSH 会话属于持续运行数据，升级时应保留。
