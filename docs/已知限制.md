# TestTracking 已知限制

本文记录当前实现边界。这里的条目不作为本阶段交付阻塞项，但修改相关模块时应重新评估。

## 1. 当前恢复保证的前提

服务端异常退出后的进度恢复目前按以下条件使用：

- `server.db_conn` 已配置，框架可以连接 PostgreSQL。
- 服务端插件使用同一 PostgreSQL 保存任务计划和 completion journal。
- run 已成功完成计划持久化，使用当前 v4 任务计划格式。
- 重启时数据库和记录可正常读取。
- manifest 与计划时一致，程序及数据版本配置与原 run 兼容。

客户端异常退出恢复还要求：

- `server.client_timeout_ms` 大于 0，才能启用心跳超时回收；仓库样例为 5000ms，代码默认值 0 表示关闭。
- 同一客户端重启保持原 `worker_id`。
- 同时运行的不同客户端使用不同 `worker_id`。

恢复语义是至少一次。已写入 completion journal 的任务不会重新派发；其他任务可以使用新 attempt 重新执行。

新建运行还会持久化执行指纹，覆盖服务端已加载插件 DLL、完整插件配置、manifest、数据版本和运行参数；
恢复时先核对该指纹，再恢复插件计划。完整插件配置中任意字段变化都可能阻止恢复，因此升级前应完成
当前运行，异常恢复时先还原原配置。旧记录仍按已有版本检查恢复。

当前 v4 计划恢复会核对持久化的程序版本、数据版本和 manifest 指纹。不匹配时 scheduler
拒绝启动并保留原 run；恢复原部署配置后可再次启动继续。`run` 中非空的数据版本会用于
计划和结果元数据，与配置的预期版本冲突时拒绝创建；客户端领取任务时也必须匹配该 run。
未配置 `expected_program_version` 时仍不校验业务程序版本，正式部署应填写该值。

恢复阶段读取 checkpoint、部署身份或 completion journal 遇到数据库查询失败、文件读取
或目录枚举失败时，scheduler 阻止启动并保留原 run；修复存储后以原配置重新启动。
读取故障不再作为将 run 标记为 `interrupted` 的依据。确认记录缺失或内容格式不支持时，
仍按不可恢复记录处理；这不表示所有存储损坏都能自动修复。

本次新增 `TaskPlugin::validateRunParameters` 改变了 C++ 插件接口，服务端和所有插件 DLL
必须同批重新编译部署，不能混用旧插件二进制。已有未完成运行应先在原版本完成；异常
恢复时保留原 DLL、manifest 和配置，恢复完成后再升级。

## 2. 本阶段暂缓项

| 事项 | 当前行为和影响 | 运行建议 |
| --- | --- | --- |
| 文件后端计划发布 | checkpoint 和 metadata 分两次原子写入；两次写入之间崩溃可能留下能恢复但不能完成的 run | 生产恢复使用 PostgreSQL；文件后端用于局部测试 |
| 旧 checkpoint 迁移 | legacy 恢复没有覆盖全部旧优先任务和历史文件 outcome，旧运行可能不能正常结算 | 升级前完成旧运行并保留旧版本工具；不要依赖自动迁移 |
| STOP/WAKE 状态重放 | STOP、WAKE 是当前 session 的一次性控制消息，`HEARTBEAT_ACK` 只确认 session 是否登记 | 当前核心验收不依赖暂停状态跨进程保存；断线后按运行状态人工确认 |
| 永久无效任务报告 | `processResult` 只有 bool，格式无效和暂时写入失败都按可重试处理，可能阻塞 run | 保持服务端和客户端插件版本一致；发现持续重试时检查 payload 和日志 |
| 网络线程运行期异常 | Server 网络线程只记录错误，Scheduler 可能仍接受控制命令 | 以进程日志和客户端连接共同监控；网络异常后重启 scheduler |
| 历史 unfinished run | 新提交运行进入每插件持久 FIFO 队列，同一插件一次执行一个；升级前遗留的多个非队列运行仍按新到旧恢复第一条有效记录 | 异常后检查旧运行；队首配置发生变化时恢复原配置或取消该队列项 |
| task ID 作用域 | 框架内存和 `tasks` 表以 `task_id` 为单一键，接口未强制全局唯一 | 插件生成 ID 时包含 plugin/run 信息；内置插件沿用 run 前缀 |
| manifest 路径边界 | 解析器尚未拒绝绝对路径和 `..`，记录的 size 也未用于客户端核对 | manifest 只由受控脚本生成并人工检查，不接收外部清单 |
| coverage 点键 | 路径使用 32 位哈希，理论上和实际都可能发生碰撞 | 当前接受该概率；需要更强准确性时改为无损路径与行号键 |
| coverage 已成功结果修复 | 已有 success outcome 时，新发布会被视为重复；缺失 cov 等局部损坏不能通过普通补跑覆盖 | 发现损坏时先备份并由维护脚本修复数据，再运行后处理 |
| coverage schema 升级 | 已支持给旧 `plugin_run_files` 增加可选大小和内容摘要列；并非所有历史列和约束都能自动迁移 | 升级前备份数据库；旧运行没有的文件大小保留未知，不自动推测 |
| coverage cov 合并超时 | 独立工具调用合并程序时没有总超时 | 在受控环境运行并监控子进程；普通贪心筛选不需要合并 cov |
| stpcompare 默认表名 | Store 代码默认 `stp_compare_results`，样例配置和脚本默认 `stp_compare_old` | 客户端和结算脚本都显式传同一个表名 |
| 同一 run 重复 plan | RunStore 会追加部分派生记录，不保证不同计划之间完整替换 | run ID 只使用一次，由 scheduler 生成 |
| 离线数据库默认配置 | 当前样例使用 `postgres`、`trust` 和宽 CIDR，适合隔离测试网，不适合开放网络 | 部署时设置明确 CIDR、认证密码和最小权限业务用户 |
| 客户端插件范围 | 支持多个插件独立 Worker 同时执行，部署使用物理客户端基础身份，任务使用插件 Worker 或物理身份匹配 | 每插件使用 `client.task_threads` 个执行槽，总并发随插件数增加；部署激活等待所有插件空闲，无机器级资源配额或插件优先级抢占 |
| 服务端与客户端版本协调 | 支持基础 Agent 首次上线和客户端页批量增量配置、内置程序匹配配置保存及带 `server_plugin.json` 的服务端插件 ZIP 安装；客户端自动重启插件 Worker，服务端安装不会自动重启或启用新插件，也不更新框架 EXE | 先完成相关未完成任务，核对服务端插件、manifest 和程序预期身份，保存后重启相应服务；升级框架继续使用兼容完整包 |
| 程序身份覆盖范围 | coverage 与 stpcompare 的制品程序自动按 SHA-256、包内入口和执行配置派生版本；自定义插件、本机路径和包外依赖的文件内容不自动计算 | 内置程序使用向导预览并保存服务端匹配配置；包外依赖一并纳入制品，本机路径仍正确维护 `version.txt` 或显式版本，数据变化仍重新生成 manifest |
| 多客户端发布协调 | 批量发布先原子预占所有空闲物理机器，再一次性写入全部部署期望；每台独立下载、切换或回退，没有跨机器同时激活或与服务端配置一起提交的整体事务 | 先核对服务端匹配版本，再逐台确认“已生效”及注册状态；一台失败不撤销其他机器的成功升级。失败版本须重新发布才会重试 |
| 更新时间窗外发布 | 可以对空闲客户端发布；预占后停止领取新任务，等待当前有效配置的更新时间窗打开再切换 | 发布确认时核对窗口；需要立即更新时在当前窗口内安排。修改窗口本身也遵守原窗口，不会越过已配置的更新限制 |
| 制品传输与缓存维护 | 已支持按完整制品摘要复用缓存，没有大文件断点续传、增量同步和自动缓存保留策略 | 合理拆分程序和数据包，预留旧版及下载空间，维护时人工清理确认不再使用的缓存 |

运行参数在创建 run 前统一处理：空字符串、纯空白和空 JSON 对象都表示无参数，非空
JSON 对象按稳定键序序列化，其他自定义文本原样保留。参数是否支持由插件的
`validateRunParameters` 决定；coverage 和 stpcompare 当前拒绝非空运行参数，业务程序
路径、参数模板和 `task_size` 仍通过插件配置设置。参数检查本身不读取客户端制品；
制品程序身份在部署预览/发布时派生，通过服务端预期程序版本参与已有的任务去重。

服务端插件安装与程序匹配配置变更会核对在线状态和持久化未完成运行；无法确认时拒绝
变更，不能通过关闭调度器绕过恢复保护。插件安装校验 scheduler 和 result service 两份
配置的 revision，配套资源先复制为完整快照，再切换配置引用；失败或异常退出使用备份
及事务记录恢复。该机制不热替换已加载 DLL，安装成功后仍需重启对应进程。

上述规范化仅用于新建运行，不回写已存运行的参数或指纹，也不迁移历史记录。旧版以
`{}`、空白等形式生成的指纹，不保证被新版去重命中；同批重编译插件本身也会改变执行
身份。原运行恢复沿用已存参数，未完成 run 仍应以原 DLL 和配置恢复完成后再升级。

## 3. 文件执行失败

客户端插件按文件保存成功或失败 outcome。服务端插件只校验任务摘要并完成任务级记账，不做文件级业务重试。coverage 后处理遇到失败、缺失或损坏结果时停止，不写入部分精简集合。

未能持久化原始结果时，客户端把任务执行视为失败；框架可以重新派发未提交 completion 的任务。永久业务失败是否自动补跑，留给插件或单独工具处理。

coverage 和 stpcompare 客户端重领任务时，都会复用已经完整入库的成功文件。STP 发布若遇到
其他 attempt 已保存成功，也按该持久化成功状态生成任务汇总，避免任务报告与文件结果矛盾。

## 4. 重复和迟到消息

每次派发包含 `run_id`、`task_id` 和新的 `attempt_id`。服务端和客户端都按当前 session/attempt 过滤消息。客户端在收到 `TASK_REPORT_ACK` 前保存并重发报告。

同一文件的成功结果采用幂等发布，迟到的旧 attempt 不应覆盖先到的成功结果。框架不能提供严格的恰好一次执行，因此插件仍需把重复执行视为正常恢复路径。

## 5. 测试边界

现有真实进程集成测试覆盖：

- 强制结束 scheduler 后恢复同一个 coverage run。
- 新 run 在真实计划持久化窗口中被强制结束后，旧 `stopped` run 恢复。
- 已完成任务在服务端重启后不重新执行。
- 恢复对账写入失败时拒绝启动，写入恢复后继续原 run。
- completion 已提交而框架报告未写入时恢复退出码证据；历史未知退出码不推定成功，成功去重与业务失败重试保持一致。
- 客户端异常退出后立即以相同 `worker_id` 重启并完成旧任务。
- 同一 `worker_id` 接管后生成新 session 和新 attempt，旧 session 消息失效。
- PostgreSQL 短时重启后的连接恢复。
- 请求数据版本与配置冲突时拒绝计划，未配置预期数据版本时仍保存请求版本。
- 先注册的客户端不能领取其他数据版本的 run。
- STP 已有完成进度时，程序版本、数据版本或 manifest 变化阻止恢复；改回后原 run 继续。
- STP 批任务中途强杀客户端后复用已成功文件，最终任务汇总与数据库 outcome 一致。
- 真实 HTTP 制品下载、客户端 Agent 切换、无效 DLL 自动回退、历史配置回滚和重启后保留生效版本。
- 客户端已记录部署失败但报告仍为应用中时，重启补发失败报告，保留旧生效版本且不再次激活失败 revision。
- Worker 异常退出时清理业务子进程并独立恢复；多插件部署切换等待所有 Worker 的任务和结果确认完成。历史版本的单插件限制已被当前多插件进程管理替代，验收以当前版本为准。
- 同内容不同文件名、普通文件与 ZIP 共享原始内容时的客户端缓存复用。

客户端超过心跳阈值后重启的代码路径已经用私有 PostgreSQL 做过专项验证，但仓库中还没有独立命名的回归用例。服务端崩溃测试也没有穷举每一条指令之间的崩溃切点。

真实 OpenCppCoverage、业务转换程序和完整 STP 数据集需要在部署环境验收。

## 6. 受控报告脚本的权限

控制台面向可信内网使用者，允许保存并运行自定义 Python 分析脚本。报告子进程用于隔离
执行失败，不是操作系统权限沙箱：脚本拥有服务账户的文件系统和网络权限，并能取得数据库
连接信息。提供给脚本的连接默认只读，但自定义代码仍可自行建立连接；真实权限边界是服务
账户和数据库账户的授权。只运行经过确认的脚本，并按分析需要配置数据库只读账户。
