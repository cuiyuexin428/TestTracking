# TestTracking 已知限制

本文记录当前实现边界。这里的条目不作为本阶段交付阻塞项，但修改相关模块时应重新评估。

## 1. 当前恢复保证的前提

服务端异常退出后的进度恢复目前按以下条件使用：

- `server.db_conn` 已配置，框架可以连接 PostgreSQL。
- 服务端插件使用同一 PostgreSQL 保存任务计划和 completion journal。
- run 已成功完成计划持久化，使用当前 v4 任务计划格式。
- 重启时数据库和记录可正常读取。
- manifest 和版本配置没有在运行中被替换。

客户端异常退出恢复还要求：

- `server.client_timeout_ms` 大于 0，才能启用心跳超时回收；仓库样例为 5000ms，代码默认值 0 表示关闭。
- 同一客户端重启保持原 `worker_id`。
- 同时运行的不同客户端使用不同 `worker_id`。

恢复语义是至少一次。已写入 completion journal 的任务不会重新派发；其他任务可以使用新 attempt 重新执行。

## 2. 本阶段暂缓项

| 事项 | 当前行为和影响 | 运行建议 |
| --- | --- | --- |
| 恢复期间的瞬时读取失败 | `restore=false` 或异常会把 run 标记为 `interrupted`，临时数据库或文件读取故障也可能终止可恢复运行 | 启动 scheduler 前确认 PostgreSQL 可用；保留数据库备份 |
| 文件后端计划发布 | checkpoint 和 metadata 分两次原子写入；两次写入之间崩溃可能留下能恢复但不能完成的 run | 生产恢复使用 PostgreSQL；文件后端用于局部测试 |
| 旧 checkpoint 迁移 | legacy 恢复没有覆盖全部旧优先任务和历史文件 outcome，旧运行可能不能正常结算 | 升级前完成旧运行并保留旧版本工具；不要依赖自动迁移 |
| STOP/WAKE 状态重放 | STOP、WAKE 是当前 session 的一次性控制消息，`HEARTBEAT_ACK` 只确认 session 是否登记 | 当前核心验收不依赖暂停状态跨进程保存；断线后按运行状态人工确认 |
| 永久无效任务报告 | `processResult` 只有 bool，格式无效和暂时写入失败都按可重试处理，可能阻塞 run | 保持服务端和客户端插件版本一致；发现持续重试时检查 payload 和日志 |
| 网络线程运行期异常 | Server 网络线程只记录错误，Scheduler 可能仍接受控制命令 | 以进程日志和客户端连接共同监控；网络异常后重启 scheduler |
| 多个 unfinished run | 同一插件按新到旧恢复第一条有效记录；更旧的记录会留待后续启动 | 同一插件一次只创建一个活跃 run；异常后先确认旧 run 状态 |
| task ID 作用域 | 框架内存和 `tasks` 表以 `task_id` 为单一键，接口未强制全局唯一 | 插件生成 ID 时包含 plugin/run 信息；内置插件沿用 run 前缀 |
| manifest 路径边界 | 解析器尚未拒绝绝对路径和 `..`，记录的 size 也未用于客户端核对 | manifest 只由受控脚本生成并人工检查，不接收外部清单 |
| coverage 点键 | 路径使用 32 位哈希，理论上和实际都可能发生碰撞 | 当前接受该概率；需要更强准确性时改为无损路径与行号键 |
| coverage 已成功结果修复 | 已有 success outcome 时，新发布会被视为重复；缺失 cov 等局部损坏不能通过普通补跑覆盖 | 发现损坏时先备份并由维护脚本修复数据，再运行后处理 |
| coverage schema 升级 | 运行时只建缺失表，不迁移旧列和约束 | 升级前备份数据库并使用与当前 schema 一致的新库或人工迁移 |
| coverage cov 合并超时 | 独立工具调用合并程序时没有总超时 | 在受控环境运行并监控子进程；普通贪心筛选不需要合并 cov |
| stpcompare 默认表名 | Store 代码默认 `stp_compare_results`，样例配置和脚本默认 `stp_compare_old` | 客户端和结算脚本都显式传同一个表名 |
| 同一 run 重复 plan | RunStore 会追加部分派生记录，不保证不同计划之间完整替换 | run ID 只使用一次，由 scheduler 生成 |
| 离线数据库默认配置 | 当前样例使用 `postgres`、`trust` 和宽 CIDR，适合隔离测试网，不适合开放网络 | 部署时设置明确 CIDR、认证密码和最小权限业务用户 |
| stpcompare 一键打包 | 通用一键部署当前主要生成 coverage 客户端，stpcompare 需要单独调用打包脚本并传插件参数 | 使用 `build_package.ps1 -Plugin stpcompare -ConverterExe ...` |

## 3. 文件执行失败

客户端插件按文件保存成功或失败 outcome。服务端插件只校验任务摘要并完成任务级记账，不做文件级业务重试。coverage 后处理遇到失败、缺失或损坏结果时停止，不写入部分精简集合。

未能持久化原始结果时，客户端把任务执行视为失败；框架可以重新派发未提交 completion 的任务。永久业务失败是否自动补跑，留给插件或单独工具处理。

## 4. 重复和迟到消息

每次派发包含 `run_id`、`task_id` 和新的 `attempt_id`。服务端和客户端都按当前 session/attempt 过滤消息。客户端在收到 `TASK_REPORT_ACK` 前保存并重发报告。

同一文件的成功结果采用幂等发布，迟到的旧 attempt 不应覆盖先到的成功结果。框架不能提供严格的恰好一次执行，因此插件仍需把重复执行视为正常恢复路径。

## 5. 测试边界

现有真实进程集成测试覆盖：

- 强制结束 scheduler 后恢复同一个 coverage run。
- 新 run 在真实计划持久化窗口中被强制结束后，旧 `stopped` run 恢复。
- 已完成任务在服务端重启后不重新执行。
- 恢复对账写入失败时拒绝启动，写入恢复后继续原 run。
- 客户端异常退出后立即以相同 `worker_id` 重启并完成旧任务。
- 同一 `worker_id` 接管后生成新 session 和新 attempt，旧 session 消息失效。
- PostgreSQL 短时重启后的连接恢复。

客户端超过心跳阈值后重启的代码路径已经用私有 PostgreSQL 做过专项验证，但仓库中还没有独立命名的回归用例。服务端崩溃测试也没有穷举每一条指令之间的崩溃切点。

真实 OpenCppCoverage、业务转换程序和完整 STP 数据集需要在部署环境验收。
