# 已知限制

本文只记录**在当前代码中已确认**的限制、约束与验证边界。标注为"未独立验证"的条目表示结论来自代码/文档阅读而非本机实测；不把推测写成事实。

- 适用平台、部署链路与安全边界均在 Windows x64 前提下成立。
- 其他文档：[需求说明](需求说明.md)（非目标）、[设计说明](设计说明.md)（恢复语义）、[部署与运行](部署与运行.md)（操作步骤）。

## 1. 平台与构建

1. **交付链路只面向 Windows x64**（`CMakeLists.txt`、`client/`、`scheduler/`、`tools/*.ps1`）。POSIX 分支会参与编译（如 `common/src/AtomicFile.cpp`、`common/src/ProcessRunner.cpp`、coverage 的 `settle_coverage.cpp`），但**没有部署目标**；非 Windows 上的行为不作为交付承诺。
2. **部署包必须是 Release**：`tools/build_package.ps1` 对非 Release 配置直接抛错，理由是 Debug 运行库不可再分发。
3. **libpq 必须在构建期可定位**：`cmake/find_package.cmake` 找不到 `include/libpq-fe.h` 与 `lib/libpq.lib` 时 CMake 直接失败；纯 Git 工作副本可能缺少 `third_party/pgsql` 与 PostgreSQL 压缩包。
4. **打包脚本默认构建目录固定**为 `build\offline_verify\bin\Release`；使用其它构建目录必须显式传 `-BinDir`，不再从历史目录（如 `build\rt`）自动选择。
5. `-utf-8` 编译选项在 MSVC 下强制生效（`CMakeLists.txt`）；源码中的非 ASCII 文本依赖该选项，移植到其它编译器时需要等效设置。

## 2. 网页与权限边界

1. **没有登录、账号与权限体系**。默认监听 `0.0.0.0:56330`，按可信内网使用；任何能访问该端口的浏览器都拥有相同操作权限（`result_service/README.md`、`result_service/app/config.py`）。
2. 现有防护是**请求校验**而非鉴权：写入类请求要求同源（由 `Host` 推导期望 origin，检查 `Origin`/`Referer`，`Sec-Fetch-Site` 不得为 cross-site/same-site，且**不信任** `X-Forwarded-*`）、JSON 写入要求 `Content-Type: application/json`（否则 415）；CLI 工具在无浏览器来源头时仍可用。
3. **DSH 助手不代表权限隔离**：它以服务器账号运行，继承该账号的模型配置、文件权限与已安装工具；部署评审工作流属于"建议+人工确认"，不是权限沙箱。
4. 浏览器操作身份（`operator_id`）用于隔离会话与聊天历史，**不是身份认证**：本机浏览器配置可伪造该标识。

## 3. 部署链路边界

1. **没有跨客户端的批量发布事务**：一次发布按客户端逐个推进；部分机器失败时整批不会回滚，需要按客户端重试或回滚。
2. **没有框架 EXE 自更新**：客户端更新代理只准备插件与业务资源；`client.exe` 与调度器的协议升级仍需整体替换兼容的包。
3. **客户端更新代理依赖 Windows PowerShell 5.1 与 .NET**，不需要 Python/npm/外网；它不是独立启动器，由 Agent 调用。
4. **客户端失败锁存**：某代一旦被判为 `failed`，只有发布新修订才会重试，即使之后下载条件恢复也不会自动激活旧代（这是为避免在没有预留的情况下激活）。
5. **制品缓存不能自愈的唯一情形**：制品按内容寻址，若**服务端对象字节本身损坏**，客户端重试只会拿到同样的坏字节；需要由服务端重新上传，必要时人工清理该客户端 `deployments\objects` 下对应的 64 位哈希目录。下载中断、临时文件、清单缺失等其它损坏均有重下/重解包路径。
6. **客户端配置补丁不能改身份与入口**：`client.worker_id` 与 `client.deployment_endpoint` 不能被补丁覆盖；`{artifact:slot}` 引用必须占满整个字符串值且不能越出制品目录。
7. 单机可跑的插件数受客户端配置与机器资源限制；统一部署管理的插件资源不能被高级配置操作覆盖。

## 4. 调度与数据库语义

1. **同一插件同时只有一个 active run**：由 `runs` 表上的表级锁加"同插件无其它 running"校验保证；该检查的前提是同一数据库实例。
2. **重复工作判定基于框架任务记录**，不读插件私有结果表：`finished` 只表示结果已收齐（含业务失败），"全部任务已上报且退出码为 0"才视为完整成功；缺少任务证据不构成成功证据。
3. **强制重跑**需要填写原因并关联最近一次等价 run；显式重跑不会绕过执行指纹校验。
4. **执行指纹会在部署变化时阻塞排队 run**：queued run 若与当前配置/manifest 不一致，会保持 `blocked` 并给出原因，同插件后续 run 继续 FIFO；恢复原部署或取消该排队 run 是仅有的两条出路。
5. **恢复受阻会阻止调度器启动**：checkpoint、部署身份或完成日志读取失败时，框架以显式错误停止启动并保留原 run，不会把它当作"丢失"处理；必须先恢复存储/原部署。
6. **调度器 stdin 的 `stop` 只按插件类型**（`stop <plugin_type>`），带 run ID 的精确停止走管理接口/网页。
7. **数据库只读语义是默认约定而非权限边界**：结果服务按只读使用数据库（配置项与环境变量决定连接），但没有任何机制阻止一个持有写权限的连接去写库；生产环境应通过数据库账号权限实现只读。（未在本机实测权限效果。）
8. 运行状态快照带 `snapshot_age_ms`；该值持续增长表示 worker 线程未刷新状态，此时界面数据是陈旧的，应查日志而不是据此下结论。

## 5. 制品、后处理与报告

1. **制品不可变**：同 kind+name+version 不同字节返回 409，需要换版本号或换名字；相同内容重复上传幂等。
2. **数据集上传不更新调度器 manifest**：数据集版本与 `stp_manifest` 仍需单独配置。
3. `coverage_settle` 的合并阶段**每轮 10 分钟超时**（多轮合并各自计时），超时或失败时旧结果保持不变，可重试；该超时目前是固定值，不走插件的 `process_timeout_ms` 配置。
4. 覆盖率合并的中间文件与最终报告路径会以 UTF-8 传给子进程；若报告读取路径落在**当前代码页无法表示**的字符上（如罕见字符），分析读取仍可能失败——这是本机未实测的窄边界。
5. 报告脚本在结果服务内部的 worker 进程里执行（不是独立进程）；超时只终止该 worker，脚本自身派生的外部进程不在其清理范围内。
6. 报告产物每次使用新的 uuid 目录，失败或超时只删临时目录，旧报告不会被破坏。

## 6. 管理接口的硬限制

调度器本机管理端口的实现约束（`scheduler/src/ManagementServer.cpp`）：

| 限制 | 行为 |
| --- | --- |
| 请求头超过 16384 字节 | 返回 431 |
| 请求体声明超过 65536 字节 | 返回 413 |
| 缺少 `Content-Length` | 返回 411 |
| 并发请求数达到 8 | **直接关闭连接**，不返回 503 |
| 仅本机使用 | 默认 `http://127.0.0.1:5556`，不是对外接口 |

结果服务侧对调度器的调用超时为写请求 35 秒、读请求 3 秒（`result_service/app/management.py`）；调度器不可用时返回 503。部署协调在推进期间会持有自己的状态锁跨这些调用，因此慢调度器会**有界地**推迟部署列表/详情类请求；状态查询与客户端发现不在这条锁上。

## 7. 兼容性与升级

1. **插件接口变更需要整体重建**：`TaskPlugin`（含 `validateRunParameters`）与 `WorkerPlugin`（含带 `CancellationToken` 的 `execute` 重载）变化时，必须同时重建并部署调度器与**全部**插件 DLL；升级前应先完成旧版本上未完成的 run。
2. 旧 run 记录缺少执行指纹时，沿用原有工作指纹与插件的恢复检查，不会因为升级本身被判为不一致。
3. 结果视图的 `PUT` 必须携带读取时的 `revision`；冲突返回 409 且不改动已存视图。注意 revision 属于 HTTP API 元数据，不写入插件 JSON。
4. 客户端 Worker 身份是 `<worker_id>`（单插件）或 `<worker_id>/<plugin>`（多插件）；**不要把斜杠写进基础配置的 `worker_id`**，两端都会拒绝。
