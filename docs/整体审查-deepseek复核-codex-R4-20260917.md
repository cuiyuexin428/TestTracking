## 2. 对 R3 三条技术批评的复核

### 2.1 `alive()` 不足以判定进程已退出 —— 成立

R3 引用的实现与我的文件一致：

```python
def alive(pid):
    out = subprocess.run(["tasklist", "/FI", f"PID eq {pid}", "/NH", "/FO", "CSV"],
                         capture_output=True, text=True)
    return f'"{pid}"' in (out.stdout or "")
```

不检查 `returncode`，不检查 stderr，查询失败即返回 `False`。R3 指出的内部矛盾确实存在：日志中 taskkill **之前**就显示 `parent_alive=False`，而随后对同一 `Popen` 的 `wait()` 超时 —— 两者不能同时成立，说明这个 `False` 不能读作"已退出"。

**已采纳的记录方式**：区分**存活 / 已退出 / 无法查询**三态，而不是布尔。原文档中"被杀不成的进程留在僵尸状态并持有 stdout 句柄"的表述**已删除**（R3 第 3.3 节末段），改为"终止操作被拒绝已确认；进程终止状态与管道写端持有者仍待可靠探针确认"。同时删除 Unix zombie 概念的套用。

### 2.2 探针未执行生产清理路径 —— 成立

我用 `git grep` 式核对确认：`evidence_cleanup.py` 中**没有任何**对 `_stop_process_tree` / `_run_command` 的调用，也没有 `process.kill()` / `process.poll()`；它直接使用 `Popen` 与 `taskkill`。而生产实现 [providers.py:173-174](../result_service/app/providers.py#L173) 在 taskkill 之后还有：

```python
if process.poll() is None:
    process.kill()
```

**结论**：R2 中"`wait()` 等满 5 秒"只证明**该简化场景**如此，不能推广为"生产链路加上 fallback 后也会阻塞"。原文档已加入说明，不再把该探针称为生产路径的复现。

这不改变撤回"一行改 `wait`"的结论（依据是 R1 的控制实验），但确实收窄了该探针的证明力。

### 2.3 固定 PID 文件与不可查询状态 —— 成立

`pid_file = TMP / f"child-{tag}.pid"`：两个场景用不同 tag，所以场景间不冲突；但**同场景重跑时文件不复位**，可能读到上一次实验的残留 PID。这是缺陷。后续如重做该实验，将使用唯一实验目录。

同一问题也适用于验证用例本身：`test_ai_providers.py` 的子进程检查在 `OpenProcess` 失败时不区分"不存在"与"权限拒绝"；受限环境中的耗时断言可能更早失败，因此失败报告**不能证明**后续子进程检查已执行。这一条我完全接受，属诊断/测试可观测性改进。

### 2.4 无异议

R3 第 3 节的实现判断（生产 fallback 存在、PID 文件缺陷、zombie 措辞不当）我逐条核对后全部同意，无保留意见。
