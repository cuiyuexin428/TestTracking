## 2. 通信协议（common/proto）

信封 `Envelope{type, plugin_type, oneof payload}`：`type` 是分发键，`plugin_type` 是路由到服务端插件的键；业务 payload 对框架不透明。

| 消息 | 方向 | 关键字段 | 触发时机 | 处理流程 |
| --- | --- | --- | --- | --- |
| REGISTER | 客户端→服务端 | plugin_type、RegisterCommand.payload（业务校验消息） | 客户端启动 INIT 阶段 | 服务端按 plugin_type 找插件 → validateClient → 回 REGISTER_RESULT |
| REGISTER_RESULT | 服务端→客户端 | plugin_found、accepted、reason、payload（业务回复） | 收到 REGISTER 后 | 客户端失败则退出；成功则调用插件 handleValidationReply（当前恒 kReady） |
| HEARTBEAT | 客户端→服务端 | ip、status(IDLE/BUSY)、resource(mem/disk/cpu)、plugin_info(版本) | 周期 1s | 服务端更新客户端表 last_seen；超时判离线 |
| REQUEST_TASK | 客户端→服务端 | count（期望任务数） | 客户端有空闲槽位时 | 服务端循环调插件 requestTask 至 count 个；无任务回 NO_TASK |
| TASK | 服务端→客户端 | run_id、tasks[](task_id + payload) | 响应 REQUEST_TASK | 客户端逐任务 ACK、入执行池 |
| TASK_ACK | 客户端→服务端 | task_id | 收到 TASK 后 | 服务端标记 acked，落库 |
| TASK_REJECT | 客户端→服务端 | task_id、reason | 客户端拒收（防御路径） | 服务端移除在飞并 requeue 到插件 |
| TASK_REPORT | 客户端→服务端 | task_id、exit_code、duration_ms、result（业务结果） | 任务执行完成 | 服务端落库、转插件 processResult |
| NO_TASK | 服务端→客户端 | 空 | 无任务可发 | 客户端退避后重试 |
| STOP | 服务端→客户端 | run_id、reason | `stop <plugin_type>` 或 quit 自动 stop | 客户端丢弃排队任务、等在飞完成、结果丢弃、进入静默 |
| WAKE | 服务端→客户端 | 空 | `wakeup [plugin_type]` | 客户端退出静默恢复拉取；正常态下 no-op |

协议边界：注册、心跳、任务、结果中的业务 payload 均以 `bytes` 透传；框架只读信封字段。

## 3. 通用基础组件（common）

### 3.1 ZMQ 封装（zmq_helper）

- `ZmqBase<SocketType>`：上下文/套接字生命周期、bind/connect、单帧/多帧收发、超时 poll、`ZMQ_LINGER=0` 防阻塞退出。
- `ZmqDealer` / `ZmqRouter`：客户端/服务端套接字；多帧消息带 identity 帧。
- `lastPeerAddress()`：收帧时读取 `Peer-Address`，服务端据此显示客户端真实地址（ip:port）。
- 线程安全：套接字不做跨线程共享（服务端收/发都在 Server 线程；客户端在主线程）。
- 错误处理：zmq 错误即致命，服务端/客户端捕获后 `std::terminate()`。

### 3.2 阻塞队列（BlockingQueue）与事件池（EventManager）

- BlockingQueue：带超时 pop、pushFront、clear；服务端收发队列、客户端完成结果队列复用。
- EventManager：N 线程事件分发；析构时停止接单、清空排队事件、等待正在执行的事件退出；客户端 TaskExecutor 复用其能力。

### 3.3 日志（Logger）与配置（Config）

- Logger：单例、线程安全、级别 Debug/Info/Warn/Error/Fatal；控制台 + 可选文件。
- Config：加载 JSON；统一约定配置文件在 exe 同目录 `config/` 下（`config/scheduler.json`、`config/client.json`），支持绝对路径参数覆盖。
- DynamicLibrary：Windows LoadLibrary / POSIX dlopen；插件工厂 `CreatePlugin` / `CreateClientPlugin` 导出。
- 跨 DLL：common.dll 导出全部符号（WINDOWS_EXPORT_ALL_SYMBOLS），插件与框架同一 CRT（Debug=/MDd），`/FI common/export.h` 统一导入导出。

## 4. 服务端框架（scheduler）

### 4.1 main（命令控制台）

命令：

| 命令 | 行为 |
| --- | --- |
| run <plugin_type> <dataset_version> [params] | 创建 run（dataset_version 透传给插件） |
| stop <plugin_type> | 停止该插件活跃 run：STOP 客户端 → 回收在飞 → 保存检查点（失败则保持活跃 run，便于重试）→ cancel → FinishRun(stopped) |
| wakeup [plugin_type] | 向客户端发 WAKE |
| clients | 打印客户端全量监控信息 |
| status | 插件数与在飞任务数 |
| quit / exit | **安全退出**：自动对所有活跃 run 执行 stop 并等待完成（≤15s）后再退出 |

### 4.2 Server（通信模块）

- 单线程 poll 循环：`waitReadable → recvMsgParts → 解析 Envelope → incoming 队列`；`outgoing 队列 → waitWritable → 发送`。
- 客户端按 identity（worker_id）路由。
- 发送队列 HWM 满时，队头消息放回 `pushFront` 后 `continue`，保持顺序并下轮重试；持续发生仍视为 P0 根因排查。

### 4.3 Scheduler（调度模块）

职责与流程：

1. 启动：加载插件 → Storage 初始化 → 恢复未完成 run（每 plugin_type 最多恢复 1 个，失败标记 interrupted）→ 启动 Server → 启动处理线程。
2. 注册：REGISTER → 按 plugin_type 找插件 → `validateClient`（覆盖率插件只做版本核对）→ 回 REGISTER_RESULT。
3. 客户端表：REGISTER/HEARTBEAT/REQUEST_TASK/ACK/REPORT 都刷新 last_seen；`client_timeout_ms=5000` 扫描离线 → 移除客户端并 `ReclaimClientTasks`。
4. 在飞记账：下发记 in_flight（identity/plugin_type/sent_at/acked）；ACK 标记；上报移除；TASK_REJECT/离线/租约回收时 requeue 到插件。
5. 批量授予：按 REQUEST_TASK.count 循环调用插件 `requestTask`，打包成 TASK 批量下发；`task_lease_timeout_ms=0`（租约关闭）。
6. run 生命周期：createRun → 插件 plan → active_runs 登记 → 完成后清理上下文 → FinishRun(finished)。
7. 退出：quit → 自动 stop 所有活跃 run（保存检查点 + 回收任务）→ 等 active_run_count=0 → 停止。
8. 恢复：启动时 `LoadUnfinishedRuns`（running/stopped）→ 插件 restore（覆盖率插件从检查点恢复当前波/剩余任务/累计点集）。

### 4.4 Storage（框架持久化）

- 表：`runs(run_id, plugin_type, dataset_version, params, status, created_at, finished_at)`、`tasks(task_id, run_id, client_identity, status, payload, ...)`。
- 写入点：SaveRun（run 开始）、SaveTask（任务下发）、AckTask（ACK）、ReportTask（上报）、ReclaimTasks（回收）、FinishRun/ResumeRun。
- 失败策略：best-effort，仅记日志不致命。

## 5. 客户端框架（client）

### 5.1 main

- 解析 `config/client.json`；启动失败打印错误日志，交互终端 `pause` 后退出（非交互自动跳过）。

### 5.2 Client（状态机主线程）

执行流程：

1. INIT：加载插件 → 设置 ZMQ identity → 探测本地 IP → 注册（REGISTER → 等 REGISTER_RESULT；被拒即失败退出）。
2. 主循环（每轮 poll 50ms）：
   - 收消息并分发（TASK/NO_TASK/STOP/WAKE）；
   - 周期心跳（默认 1s，带 ip/status/资源/版本）；
   - 上报已完成任务结果（完成队列 → TASK_REPORT）；
   - **计数驱动拉取**：`free_slots = task_threads - in_flight - outstanding_requests`；有槽位且无未应答请求时发 REQUEST_TASK(count=free_slots)。
3. STOP 处理：executor.stop()（丢弃排队、等在飞完成、结果丢弃）→ 清完成队列 → 重启 executor → 置 `silent_` → 不再发 REQUEST_TASK（心跳保持）。
4. WAKE 处理：`silent_=false`、重置退避；正常态收到 WAKE 仅重置退避（no-op）。
5. **会话失活自动重注册**：若客户端空闲（in_flight=0）且某次 REQUEST_TASK 在 `request_timeout_ms`（默认 5000）内无应答，判定会话已失活（如服务端重启后忘记该客户端），则清空 outstanding 并重新 REGISTER 获得新 session，恢复拉取；避免“服务端重启后客户端再也请求不到任务”。
6. 退出：输入 quit 或 stdin EOF 时 stop()。

### 5.3 TaskExecutor

- 基于 EventManager 的 N 线程池；`push(task)` 把“execute + 完成回调”封装为事件。
- `stop()`：置取消标志、丢弃排队事件、join worker（在飞任务执行完，但完成回调被取消，结果不回流）。

## 6. 插件接口（common）

### 6.1 TaskPlugin（服务端插件）

| 接口 | 语义 |
| --- | --- |
| pluginType() | 唯一类型键，注册/路由锚点 |
| init(config) | 校验业务前提（manifest、期望版本、存储等） |

| saveCheckpoint / restore | 停止/重启恢复 |

调用线程：processResult 在结果池线程；其余在调度线程。

## 7. 覆盖率插件（plugins/coverage）

### 7.1 服务端 SchedulerPlugin

配置项：

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| stp_manifest | 必填 | 数据集清单（相对路径,大小） |
| task_size | 25 | 任务内文件数（可配置；单文件任务即设 1） |
| expected_program_version / expected_dataset_version | 空=不校验 | 注册版本门禁 |
| store_type / db_conn / store_dir | file | CoverageStore 后端 |

> 说明：`batch_size`、`store_cov`、`keep_staging`、`opencppcoverage` 已从服务端插件移除——这些属于结算/后处理，由独立工具 `coverage_settle` 承担。

执行流程：

1. validateClient：解析 `CoverageClientInfo{program_version, dataset_version}`，与期望版本比对，通过才 accepted（无部署、无共享目录逻辑）。
2. plan/BuildTasks：读 manifest → 直接按 `task_size` 把文件打包成任务（扁平任务池，无波次；文件大小只用于清单，不再参与排序/切波）。
3. requestTask：回收任务（priority 队列）优先 → 普通队列；派发时记录 task_client。
4. processResult：按 task_id 从 task_client 移除并计入 done；按文件统计 ok/fail/covered_lines；每次保存检查点。**不做结算**。
5. requeue：回收任务进优先队列。
6. saveCheckpoint/restore：扁平检查点（v3）。**remaining_tasks 持久化所有未完成任务（待派发 + 在飞 + 回收），restore 时全部重新派发**，因此 STOP/崩溃不会丢失在飞任务。

#### 任务粒度方案对比（可配置：task_size）

框架语义不变：Task 是原子单元，客户端框架按任务执行、不拆任务；任务内文件是插件内部的串行执行。`task_size` 决定“一个任务包含几个文件”。

| 维度 | 方案 A：单文件任务（task_size=1） | 方案 B：一组文件任务（task_size=25，默认） |
| --- | --- | --- |
| 框架原子语义 | 一致（Task=文件） | 一致（Task=一组文件，客户端不拆） |
| 任务数 | 任务数 = 文件数 | 任务数 = 文件数 / 25 |
| 请求/授予频率 | 每完成一个文件补拉一次 | 每完成一组文件补拉一次 |
| 回收/断点粒度 | 精确到文件 | 精确到任务 |
| 幂等跳过 | 按文件查库（loadFileCoverage），实现相同 | 按文件查库，实现相同 |
| 在飞/检查点规模 | 大（每文件一个 task_id） | 小 |
| 负载均衡 | 更细 | 较粗，但多客户端下仍由请求驱动 |
| 进度/监控粒度 | 每文件一个结果 | 每任务一个结果 |
| 消息量 | 较多 | 较少 |

结论：两者都不破坏“任务与执行粒度一致”的约定。默认取 25 文件/任务（消息少、检查点小、请求频率低）；需要更细回收/进度粒度时把 `task_size` 设为 1 即可。

### 7.2 客户端 ClientPlugin

配置项：dry_run、program_dir、stp_root、export_dir、opencppcoverage、target_exe、occt_dlls、store_type/db_conn、store_cov、keep_reports、dry_run_delay_ms（测试用）。

执行流程：

1. init：解析配置 → 读取 `program_dir/version.txt`、`stp_root/version.txt` → 初始化 CoverageStore。
2. collectRegistrationInfo：上报两个版本号。
3. execute：解析 CoverageTask → **循环执行任务内多个文件**，每个文件：查库幂等（已有点集则跳过）→ dry_run 合成 / 真实 OpenCppCoverage 执行 → 解析 cobertura 成点集 → 写原始行 `coverage_file_points`（+ store_cov 时写 `coverage_cov_files`）→ 返回 `FileCoverage{file, ok, covered_lines}`。
4. heartbeatInfo：`program=<v>,dataset=<v>`。

### 7.3 CoverageStore（存储抽象）

接口（节选）：saveFileCoverage / saveFileCov / loadFileCoverage / saveCheckpoint / loadCheckpoint。

- File 后端：`store_dir/<run>/<fnv>.json`、`<fnv>.cov`、`checkpoint.bin`；PostgreSQL 后端：扁平业务表（见 §8）。
- 写失败返回 bool；客户端据此把文件标记为 not ok。
- **原始点集/cov 行永久保留**，由后处理工具 `coverage_settle` 消费，结算后不清空。

## 8. 数据库设计（PostgreSQL）

| 表 | 用途 | 写入时机 | 清理时机 |
| --- | --- | --- | --- |
| runs / tasks | 框架 run/任务状态 | run 开始、下发、ACK、上报、回收 | 无保留策略（待定） |
| coverage_file_points | 每文件点集（原始行） | 客户端每完成一个文件 | **永久保留** |
| coverage_cov_files | 每文件 cov（原始行） | 客户端（store_cov 时） | **永久保留** |
| coverage_selected | 最小集合（文件相对路径） | 后处理 coverage_settle | 无（每 run 一份） |
| coverage_run_summary | run 汇总（含覆盖率） | 后处理 coverage_settle | 无 |
| coverage_cumulative_cov | 每 run 合并后的累计 cov | 后处理 coverage_settle | 无 |
| coverage_checkpoints | 每 run 检查点 | 计划/结果/STOP | 无（run 完成后保留） |

## 11. 待确认 / 风险

1. 任务粒度（task_size）是配置项，无需改代码即可在“单文件任务”与“一组文件任务”之间切换；切换会影响任务数、在飞/回收粒度、检查点规模、请求频率（对比见 §7.1）。
2. 单文件任务下 task_id 数量 = 文件数，检查点体积与 tasks 表行数上升。原始点集/cov 行永久保留，数据量随时间增长。
3. 覆盖率结果受 OpenCppCoverage 抖动影响（同一文件重复执行可能有数行差异）；幂等跳过只对“已入库文件”生效，不保证与理论值逐行一致。
4. 若启用 task_lease_timeout（当前关闭），长时间任务会被租约误回收造成重复执行。
