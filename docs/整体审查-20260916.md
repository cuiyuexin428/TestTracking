## 确认的问题

### 1. P1：Windows DSH 命令无法可靠传递报告上下文和带空格的路径

位置：[providers.py:143](../result_service/app/providers.py#L143)、[providers.py:257](../result_service/app/providers.py#L257)。

`.cmd`/`.bat` 被包装为 `cmd.exe /d /c`，完整提示词再作为命令行参数传入。cmd 会再次解释引号和特殊字符，并且存在命令行长度限制。真实同结构包装器复现：含空格安装路径启动失败；传入当前 coverage 报告源码后出现 `< was unexpected at this time.`；9,000 字符上下文出现 `The command line is too long.`。

“AI 生成报告”正常就会携带脚本、数据库结构等上下文，因此不是极端输入。路径问题同时影响 DSH 原生 Web 启动。应避免通过 cmd 传输完整提示词，使用 DSH 支持的输入/桥接机制，并验证便携安装与 npm 安装两条路径。

### 2. P2：仅更新客户端会覆盖原来的部署配置

位置：[build_package.ps1:292](../tools/build_package.ps1#L292)。

`-OnlyClient` 只保留原业务可执行文件名，随后重建整个 `config/client.json`。隔离打包验证中，原 `worker-production-07`、8 线程、production 数据库被改为 `worker-1`、2 线程、testtracking/postgres。还会覆盖插件的其他个性化配置。

内网修改源码后更新客户端框架是正常流程；这个行为会导致连接错误或多机使用同一身份。应保留已有配置，只覆盖显式指定的参数。

### 3. P2：一键构建与 STP 打包读取的二进制目录不一致

位置：[build_package.ps1:115](../tools/build_package.ps1#L115)、[setup_offline_server.ps1:146](../tools/setup_offline_server.ps1#L146)、[部署与运行.md:167](部署与运行.md#L167)。

一键部署默认编译到 `build/offline_verify`；文档的 STP 打包命令没有指定 `-BinDir`。打包器优先搜索 `build/rt`，且搜索列表不包含 `build/offline_verify`。

复制整个源码目录后在内网重编译，再照文档生成 STP 客户端包，会选中一起复制过来的旧 `build/rt`；若没有旧目录则报找不到客户端。应统一构建产物来源，部署命令显式使用本次构建输出。

### 4. P2：DSH 超时不保证回收真正的子进程

位置：[providers.py:261](../result_service/app/providers.py#L261)。

`subprocess.run(timeout=...)` 超时只终止外层 cmd，Node/DSH 子进程可能继续持有输出管道；Python 后续等待管道关闭，超时无法按时返回。临时包装器配置 0.2 秒超时、子进程执行 2 秒，实际 2.05 秒才返回超时。如果子进程一直挂住，聊天按钮会持续处于等待状态。

应在超时时终止整棵所属进程树并回收管道。

### 5. P2：通用聊天页的 DSH 连续追问没有会话上下文

位置：[providers.py:391](../result_service/app/providers.py#L391)、[app.js:813](../result_service/web/app.js#L813)。

每次 DSH 请求都创建一次新的 headless 执行，忽略 `conversation_id`，前端也不提交聊天历史。捕获第二次调用时没有第一次问题、回复或会话参数。因此“按上面的方案修改”等追问会丢失上下文，与连续聊天界面的语义不同。原生 DSH Web 页签的会话机制不受此问题影响。

应接入 DSH 会话恢复能力或维护明确的消息历史。

### 6. P2：启动运行的数据版本参数与插件记录不同

位置：[coverage/SchedulerPlugin.cpp:30](../plugins/coverage/src/SchedulerPlugin.cpp#L30)、[stpcompare/SchedulerPlugin.cpp:30](../plugins/stpcompare/src/SchedulerPlugin.cpp#L30)。

两插件计划时忽略 `RunRequest.dataset_version`，插件元数据使用初始化配置。实际执行 `run coverage d2`，当部署配置和客户端仍为 d1 时任务照常完成，数据库得到 `runs.dataset_version=d2`、`plugin_runs.dataset_version=d1`。如果预期配置为空，命令传入的版本也不会进入分析目录。

应统一版本来源，启动时拒绝与部署配置矛盾的请求。证据位于 `build/test/runtime-integration-kdtd3gsu`。

### 7. P2：STP 崩溃重领后，任务失败与数据库成功结果可能矛盾

位置：[stpcompare/ClientPlugin.cpp:220](../plugins/stpcompare/src/ClientPlugin.cpp#L220)。

STP 重领整个任务时仍会执行已成功入库文件。存储层保留原 success 并返回发布成功，但任务报告使用本次执行的失败状态。实测一个任务包含 a/b：a 已入库、b 执行中时杀客户端；重启后 a 第二次执行失败、b 成功。最终任务 `exit_code=1`，数据库 a/b 却都是 success、原始结果齐全。

应复用已持久化成功结果，或依据最终被数据库接受的 outcome 形成任务报告。证据位于 `build/test/runtime-integration-bhlaokdw`。

### 8. P2：未完成文件数量在两个分析字段中互相矛盾

位置：[repository.py:234](../result_service/app/repository.py#L234)。

`pending_files` 只统计显式 pending outcome，但尚未执行的文件没有 outcome。私有 PostgreSQL 验证：计划 2 个、成功 1 个时，`result_readiness.missing_files=1`，同时 `result_completeness.pending_files=0`。

这些字段会提供给 AI 和自定义视图，可能生成错误分析。应从同一份完整性计算结果派生字段，并明确“尚无结果”和“执行失败”的区别。

### 9. P2：低高度窗口下 AI 输入区与发送按钮溢出

位置：[style.css:209](../result_service/web/style.css#L209)、[style.css:232](../result_service/web/style.css#L232)、[style.css:257](../result_service/web/style.css#L257)。

默认 120% 字号时，聊天区固定最小高度与侧栏可用高度冲突。在 1366×768 初始视口中，发送按钮顶部约为 770px，整个按钮在屏幕下方；1280×720 时固定侧栏的发送按钮底部约为 732px，发生截断。

应让消息区真正收缩和滚动，将输入区固定在可视侧栏内部，并同时验证字体放大。当前侧栏左右调整能工作，问题集中在高度分配。

### 10. P2：100 条之外的历史运行无法通过界面查看和分析

位置：[app.js:434](../result_service/web/app.js#L434)、[server.py:148](../result_service/app/server.py#L148)。

历史页固定加载最新 100 条，分析目录也固定 100 条，没有分页、搜索或按 run ID 打开入口。私有数据库插入 101 条后，旧 `smoke-run` 仍能通过详情 API 读取，但从历史列表和分析选择器消失，已有报告也失去正常访问入口。

应提供分页或按 run ID 查询，并在刷新时保留已选择的历史运行。

### 11. P2：界面承诺 scheduler 日志落盘，发布包实际只保存结果服务日志

位置：[index.html:93](../result_service/web/index.html#L93)、[build_server_package.ps1:403](../tools/build_server_package.ps1#L403)。

日志页提示 scheduler 和结果服务日志均在 `data/logs`；实际 scheduler 仅附着控制台，没有文件重定向，也没有调用 Logger 的文件输出接口。异常退出后，无法按提示查到历史调度日志。

应在保留 stdin 交互能力的同时落盘日志，或至少先修正文案，不能把尚未实现的行为当作已有能力。

## 已知边界与升级风险

以下与已确认缺陷分开记录，避免把明确限定的恢复范围扩大成新需求。

- **更换版本后恢复旧 run 会混用数据。** 两插件 `restore()` 没有对照原 run 的持久化版本，而注册校验读取当前配置。已实测 a.stp 用 v1、恢复后的 b.stp 用 v2，但运行仍声明 v1/d1。`docs/已知限制.md` 已明确恢复要求 manifest 与版本不变，因此这不算现有固定版本恢复承诺的新违约。用户准备在内网调整代码，升级流程必须明确先完成/终止旧 run；建议增加版本不匹配保护，保留旧进度并阻止错误继续，而不是直接将其永久标记 interrupted。证据：`build/test/runtime-integration-7ovwo13w`。
- **普通同版本异常恢复未发现新的确定性任务丢失。** 现有 session/attempt、先持久化后确认、完成日志和重领路径有测试支撑；STP 报告一致性问题仍需修复。
- **分析与执行基本分离。** 独立报告读取数据库，生成报告不要求 scheduler/client 在线；原始结果和后处理汇总没有被混为一个必需步骤。
- **数据库只读契约有一处不严谨。** `repository.py:77` 在事务已开始后设置 `default_transaction_read_only`，实测当前事务仍为可写。现有内置 adapter 仅 SELECT，报告 worker 已正确设置只读，未复现业务损坏。建议统一连接级只读设置，并继续使用部署说明中的只读数据库账号。
- **客户端实时状态和日志页仍是占位页面。** 当前不能从页面检查在线客户端、心跳或读取日志；“插件与配置”只展示适配器信息，不是完整部署配置编辑器。它们不阻断任务执行，但界面还不属于功能齐全的运维控制台。
- **没有在本次范围中要求新增登录鉴权或数据传输。** 保持可信内网、每客户端完整本地数据的部署约定。

## 界面与交互评价

1920×1080 下导航、任务进度和 AI 侧栏层次清楚，主色与状态色基本一致。真实 Python 报告的生成、筛选、脚本替换均可用。

除发送按钮溢出外，1280 宽度附近的客户端导航文字会被拆行，较窄主区的报告操作按钮换行位置不整齐；固定侧栏会遮盖右侧主区。建议优先保证输入与主要操作始终可达，再统一按钮换行、导航宽度和占位页说明。不需要整体推翻现有视觉风格。

历史页标题写“最近完成的运行”，数据却未过滤执行状态；运行总览的“正在运行”来自持久记录，不能证明 scheduler 进程在线。建议让文案准确说明记录状态，实时进程在线信息待管理接口提供。

## 复制源码到内网的条件

1. 已有项目运行材料包含 C++ 第三方安装产物及源码下载缓存、PostgreSQL、嵌入式 Python、分析 wheelhouse；DSH 需另外携带修正版离线包。
2. **VS2022 C++ 工具链、Windows SDK、CMake 的离线安装材料不属于当前运行依赖包。** 内网机器若已经安装可以直接使用，否则需要另备开发工具离线安装源。完整测试还需要可找到的 Python 和 Node；项目 Python 可显式传给 CMake，DSH 包的 Node 也可显式指定。
3. `build/rt/CMakeCache.txt` 保存当前源码绝对路径及开发机 Python/Node 路径。复制后应使用新的构建目录重新配置，不能把旧缓存视为可移植构建环境；无需删除源代码或业务数据。
4. 打包时显式传本次 Release 的 `-BinDir`。修复本报告问题后重新生成服务器和客户端包，避免携带旧包。
5. 正式 STP 全量数据、业务 EXE/DLL/资源、OpenCppCoverage、内网模型端点仍由目标环境提供。每个客户端保持独立且稳定的 worker_id，服务端与客户端版本、manifest 一致。
6. 最终仍需内网双机验收：真实任务入库、报告、DSH 对话，以及服务端和客户端分别异常退出后恢复。本轮没有将本机隔离测试等同于真实内网验收。

## 修复顺序建议

先修 DSH 命令传输/超时和客户端更新/构建产物选择；再统一 run 版本、STP 报告与分析完整性语义；然后修侧栏高度、历史访问和日志落盘。补充的回归测试应覆盖这些真实复现，不增加与当前目标无关的边界测试。版本升级保护按明确的升级流程处理。
